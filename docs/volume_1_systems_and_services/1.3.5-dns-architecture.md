## 1.3.5.1 DNS Architecture

BIND9 runs as an **authoritative-only** server (recursion disabled). It serves:
- Internal forward zones defined in the `dns:` block of the vars file (`dynamic_zone_var` key resolved to `domain` at render time)
- Each zone with `zone_authority: true` gets an NS A record pointing to `host_ip`
- Reverse zones (PTR) generated at apply from A and AAAA records by `fabriclib/dns/reverse_zones.py`. There is one `/24` `in-addr.arpa` zone per IPv4 subnet and one `/64` `ip6.arpa` zone per ULA prefix, with one PTR per address. Only private addresses (RFC 1918, 100.64/10, ULA) get one; zones written by hand in `dns:` are left alone. See [operations.md](../volume_3_operations/3.2.5-reverse-dns.md#3251-reverse-dns)
- RFC2136 updates, deny-by-default: per key `records` → only `_acme-challenge.<record>.<zone>`; `primary` → `subdomain _acme-challenge`; explicit `any_name` → `zonesub`; plus the grants of any ACL policy (`bind_acl_policies`) the key is a member of. Keys live in vars, their secrets with fabric's secrets in OpenBao (managed with `fabricctl tsig`)

BIND9 answers plain DNS itself; nginx fronts only DNS-over-HTTPS:

```
host_ip:<bind_dns_port> TCP/UDP → bind9:53     plain DNS (published by Docker)
:443 dns.<domain>/dns-query     → bind9:8053   DNS-over-HTTPS (nginx terminates TLS)
```

`bind_dns_port` (default `53`) is the Docker host port mapped to BIND9's internal port 53, published on `host_ip` only (so it does not clash with `systemd-resolved` on loopback). DNS-over-TLS (853) is not exposed yet.

## 1.3.5.2 DNS with Samba AD (planned)

Design for the owner's approval ([2.11.2.6](../volume_2_technologies_and_features/2.11.2-samba-dc.md#21126-dns)); proven
by the spike (Q2, Q14).

- BIND stays the only DNS server. It serves the AD zone from the DC's database through Samba's DLZ module; the DC's
  own DNS server is off. Windows and Linux members register their names with Kerberos-signed (GSS-TSIG) updates;
  unsigned updates are refused in every zone.
- **`ad.<domain>` mode** (recommended when the fabric may federate, D87): fabric's zones are unchanged; the AD zone
  is one more zone in BIND.
- **Same-domain mode** (AD's domain = fabric's): DLZ owns the whole zone, so fabric's zone file goes and fabric's
  records are written into AD's zone (by fabric's deploy, on the DC). AD's zone takes only Kerberos-signed updates,
  so **TSIG keys cannot write there** (`REFUSED`): ACME DNS-01 works through `_acme-challenge.<name>` CNAMEs into
  `acme.<domain>`, a small zone of BIND's own that accepts fabric's TSIG keys with the grants of 1.3.5.1. fabric
  writes the CNAME when a TSIG key is given a name.
- A site with a DC serves the AD zone from its own DC; a site with none forwards `ad.<domain>` to its parent's
  BIND (1.8.8).
