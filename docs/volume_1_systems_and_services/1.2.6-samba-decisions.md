## 1.2.6.1 Decisions for the owner

**Answered 2026-10-04 (S1–S6, with D87–D92 added after the spike's first runs):** the owner chose to replace 389-DS with Samba AD, gated by the S0 spike; the answers
and the impact assessment are in [5.8.1](../volume_5_notes_and_troubleshooting/5.8.1-samba-replaces-389ds.md). The
proposals below were the questions as asked.

| # | Answer (2026-10-04) |
|---|---|
| S1 (D73) | Samba AD replaces 389-DS as fabric's one directory (people, groups, ids, devices, passwords), if the S0 spike proves it |
| S2 (D74) | One domain; an OU per site with rights delegated to its admins; configuration, schema and Group Policy replicate everywhere. **Revised 2026-10-04:** each site chooses its DC type — writable, read-only or none — and can change it later (demote and re-join); site DCs are independent and resync after being offline; each DC may write only its own site's OU by default, its limits listed with overrides in the Federation tab; the root DC holds the domain-wide roles |
| S3 (D75) | The host's address; BIND serves the AD zone through Samba's DLZ plugin |
| S4 (D76) | Linux machines join AD (confirmed by the owner 2026-10-04); login and sudo rules come from AD (Q9) |
| S5 (D77) | The trusts fabric's services need (its root CA) are pushed by default; every other policy is optional, set through an ADMX-driven editor in fabric's menus (or the standard tools). fabric ships its own ADMX templates and a blank starter template, and links to Microsoft's templates, which are not shipped (licensing) |
| S6 (D78) | The DC's certificates come from Step-CA like every service; external CAs and Let's Encrypt are a separate milestone |
| D87 | **The AD domain name** is chosen at setup, with no default, and cannot be changed later. Sites get the domain from their invitation. **Revised 2026-10-04 (owner): same-domain mode is dropped** — the AD domain is never fabric's own domain (nor a parent of it). **The suggestion is a protected sibling** at the top of the organisation's name, apart from the sites' names: `ad.` plus the first node's domain without its first label (`lan.j-j.family` → `ad.j-j.family`); a sub-domain such as `ad.lan.j-j.family` stays allowed. Reasoning: 5.8.1.13 |
| D88 | **Layout:** everything fabric manages lives under `OU=sites`, one OU per site; the root site's OU also holds the organisation-wide items (address plan, shared roles and groups). AD's own containers stay as they are; its default containers for new users and machines point to site OUs |
| D89 | **Passwords:** the admin sets the whole password policy at setup — no fabric defaults, nothing preselected; an unattended setup refuses without it; changeable later in the menus. fabric's one-time passwords are generated to satisfy the policy |
| D90 | **Access:** people and machines are tracked across the whole domain, but access is authorized per site: by default a site's people may log on only to that site's machines (logon rights per site OU, enforced on Windows and, through SSSD, on Linux), and the same per-site groups govern 802.1X and web sign-in. Access to another site's equipment is granted explicitly, or by a blanket policy set as an override in the Federation tab |
| D91 | **Every site runs the full stack**, whatever its DC type (writable, read-only or none): no reduced site profile. A site's choices stay general fabric settings; which sites the owner runs read-only is the owner's deployment, not fabric's design |
| D92 | **Links between sites are outside fabric:** WireGuard (or any other tunnel) is run by another stack; fabric assumes routed connectivity between its sites and federates over it. The "edge role" of 2.11.1.13 is not part of fabric |

The questions as asked:

| # | Question | Proposal |
|---|---|---|
| S1 | **Where passwords live** | 389-DS stays the source of truth; passwords reach Samba when set (fabric functions, a Keycloak mapper, Samba's syncpasswords back). Alternatives: (b) AD becomes the source of people and passwords and Keycloak federates to AD — simpler password flow, but fabric's directory would follow AD and the M5 design changes; (c) 389-DS's Windows-sync plugin — legacy, unproven with Samba |
| S2 | Site DCs | Read-only DCs if S0 proves them; else full DCs |
| S3 | The DC's address | Its own LAN address (macvlan) — not a host change; the host's firewall does not cover it (shown as a relaxation) |
| S4 | Linux joins | AD (`realm join`), with sudo rules kept in 389-DS |
| S5 | Default GPOs | Time, 802.1X profile, fabric's root CA; nothing else unless asked |
| S6 | Let's Encrypt through Cloudflare | Its own design after this one ([2.11.1.13](../volume_2_technologies_and_features/2.11.1-samba-ad.md#211113-related-separate-designs-after-this-one)) unless pulled forward: it is single-host and testable now |

## 1.2.6.2 Decisions raised by the rewritten design (D93–D105)

Raised 2026-10-04 by the rewritten directory design ([1.6.3](1.6.3-samba-directory.md),
[1.8.8](1.8.8-federation-on-ad.md), [2.11.2](../volume_2_technologies_and_features/2.11.2-samba-dc.md)). **Answered
2026-10-04:** the owner approved the design with every proposal below as written, except D99, removed from scope;
D101 was added with the approval. Reasoning: [5.8.1.11](../volume_5_notes_and_troubleshooting/5.8.1-samba-replaces-389ds.md#58111-the-owner-approves-the-rewritten-design).

| # | Question | Proposal |
|---|---|---|
| D93 | AD accepts a previous password for network sign-ins for 60 minutes after a change (Q7) | Off (0 minutes): a changed password stops working at once; settable (`ad_old_password_minutes`) |
| D94 | SYSVOL between DCs (Samba replicates GPO objects, not their files) | Each GPO owned by the site it is linked to (the root for domain GPOs). **Revised 2026-10-05 (owner):** every DC pulls the GPO folders it does not own from their owner's DC **over SMB**, signed in as its own machine account (445 is already open between DCs), on the condition that SYSVOL and NETLOGON are **never advertised**: not browseable, no NetBIOS, no mDNS, no WS-Discovery ([1.8.8.15](1.8.8-federation-on-ad.md#18815-group-policy-between-sites-over-smb)). Was: over the federation endpoint (mutual TLS). Reasoning: [5.8.1.21](../volume_5_notes_and_troubleshooting/5.8.1-samba-replaces-389ds.md#58121-the-owners-s8-answers) |
| D95 | Site-scoped groups (revises F4, D63: created in the root site's directory) | `<site>-<role>` groups live in the site's own `OU=groups`, created by that site's admins or the root's; organisation-wide groups in `OU=organisation` |
| D96 | Roaming between sites (revises F3, D62: replication by consent) | With one domain every DC holds every site's objects, so consent becomes an **access grant** (D90): explicit or blanket, per site, applied to log-on, 802.1X and web sign-in together (1.6.3.10) |
| D97 | uid/gid numbers when writable site DCs create people while cut off | Each site gets its own id block from its parent at join (`posix_id_block`, default 100 000): the next block after every one the domain holds, so a nested parent (D105, 2026-10-05; was: from the root) never repeats another branch's; the root's block keeps today's numbers |
| D98 | How the DC gets the host's address (S3) | The host network, LAN interface only, like Kea (AD advertises its own address, which NAT would get wrong); proven with a Windows join in S1 |
| D99 | *[DELETED] Moving existing installs from 389-DS.* This item has been removed from scope of fabric as of (0.5.0 / 2026-10-04). See D101 for newest applicable method | — |
| D101 | Installs and upgrades before the **1.0 milestone release** (version 1.0.0, D37) (owner, with the approval) | There are no users to keep updated until the 1.0 milestone release, which comes only after thorough testing of the whole stack. Until then: no migrations and no upgrade paths are designed or built; installs are rebuilt. Suspends D39 until then. **Revised 2026-10-07 by D113:** the line moves to 0.6.1 |
| D100 | Time for Windows members | Their default (signed NTP from their DC), answered by the host's chrony through the DC's signing socket; no time GPO |
| D102 | Which domain machines PEAP admits, and on what VLAN (S3.3) (owner, 2026-10-05) | The `radius_people` group mappings, as for people: an enabled computer in the site's `OU=machines` is admitted when one of its groups (e.g. Domain Computers, or one the admin makes) is mapped, on that mapping's VLAN; no mapping, no machine access. Reasoning: [5.8.1.16](../volume_5_notes_and_troubleshooting/5.8.1-samba-replaces-389ds.md#58116-s3-freeradius-on-ad) |
| D103 | Who administers a site (S6.3; owner 2026-10-05) | Five **roles**, each its own group in the site's `OU=groups` so each can be given to a different admin group: `<site>-ou-admins` (the site's OU: people, groups, sub-OUs), `<site>-machine-admins` (add, enable and remove the site's machines and devices), `<site>-gpo-admins` (the site's own GPOs, and blocking inheritance of what a parent did not enforce), `<site>-linux-sudo` (any command as root on the site's joined Linux machines), `<site>-windows-admins` (local Administrators on the site's Windows machines). `<site>-admins` is a member of all five by default. A parent site's roles reach every site below it and a child cannot block them (D105); no role may change or bypass a parent's enforced controls. Everyone else gets sudo only from rules an admin adds. Reasoning: [5.8.1.21](../volume_5_notes_and_troubleshooting/5.8.1-samba-replaces-389ds.md#58121-the-owners-s8-answers) |
| D104 | Where the Federation tab's overrides and access grants are kept (S8.6; owner 2026-10-05) | A `fabric` database, with its own role, in each site's Postgres (the server Keycloak already uses). Each row is owned by the site that made it and only the owner writes it; every site holds a copy of every row, kept by Postgres's logical replication along the site tree (each site with its parent; a link carries only the rows the other side does not own, so nothing loops). **Postgres is never on the host:** a link reaches it through nginx's stream proxy on one port open to the linked sites' addresses only, mutual TLS with the site's certificate (its name checked against the registry), then a Unix socket nginx and Postgres share (no network on the inner hop: TLS there is not possible, nginx's stream proxy cannot speak Postgres's direct TLS; the owner's "TLS inside if it can be done, not a requirement"), and a per-link replication role whose password is in OpenBao (spike: 5.8.1.25). The effects (ACLs, GPOs, FreeRADIUS and Keycloak changes) are written to AD as before. Other fabric state stays where it is; moving any of it is its own decision ([1.8.8.16](1.8.8-federation-on-ad.md#18816-where-overrides-and-grants-are-kept)). Reasoning: [5.8.1.21](../volume_5_notes_and_troubleshooting/5.8.1-samba-replaces-389ds.md#58121-the-owners-s8-answers) |
| D105 | Nesting in the directory (S8.8; owner 2026-10-05; replaces 1.8.8.6's flat layout) | A site's OU is placed **in its parent's OU** (the root's OU is the top, under `OU=sites`) and **inherits by default**: Group Policy through AD's GPO inheritance and permissions through AD's ACL inheritance, from the domain down. A parent links a GPO **enforced** for a control its children may not change; anything else a child may override with its own GPO or by blocking inheritance. A parent's roles (D103) and agent reach every site below it. A site with no DC reads and writes through its nearest ancestor that has one. Re-parenting moves the OU ([1.8.8.14](1.8.8-federation-on-ad.md#18814-nesting-and-inheritance)). Reasoning: [5.8.1.21](../volume_5_notes_and_troubleshooting/5.8.1-samba-replaces-389ds.md#58121-the-owners-s8-answers) |

Approved with them: the privileges inventory, D49 ([1.3.9](1.3.9-container-inventory.md)); the re-planned build
steps S1–S8 ([2.11.2.12](../volume_2_technologies_and_features/2.11.2-samba-dc.md#211212-build-plan)); F10
(D69, the base DN) is superseded by D87.

## 1.2.6.3 Sign-in on the domain (D106–D111)

**Answered 2026-10-07 (owner):** password-free sign-in for people on the domain, with the client certificate and
the authenticator kept as layers to add. Replaces D48's web UI client certificate when built. Reasoning and the
impact assessment: [5.8.2](../volume_5_notes_and_troubleshooting/5.8.2-sign-in-on-the-domain.md).

| # | Question | Decision |
|---|---|---|
| D106 | How people on a domain device sign in without a password or MFA | **Both:** Kerberos from the domain logon (Keycloak's Kerberos authenticator) by default, and a per-user certificate in the person's profile (Keycloak's X.509 authenticator); off the domain, password and TOTP |
| D107 | The web UI from a domain device | ~~Signed in by the domain, then asks for TOTP by default~~ **Revised 2026-10-07 by D110:** no second factor by default; TOTP or a passkey is raised from the web console |
| D108 | The web UI's client certificate (D48: always required) | An **option, off by default**, easy to turn on after the first standup; status output and the web UI show whether it is on |
| D109 | When | **After 0.6.0**, tested on the owner's Proxmox lab; **0.6.x** (owner 2026-10-07, 1.1.4.6) |
| D110 | What a new install asks at sign-in (owner 2026-10-07) | **A username and password, for everyone, admins included**; Kerberos from the domain logon on by default. A deviation from global Rule 10 ([1.2.3.2](1.2.3-deviations.md#1232-sign-in-starts-at-a-password-d110)) |
| D111 | Raising and lowering sign-in security (owner 2026-10-07) | **Raised from the web console** (TOTP, a passkey such as Windows Hello, a per-user certificate, the web UI's client certificate); **lowered only at the command line** on the fabric host, as root, with the layer's name typed to confirm (`--yes` does not skip it), an audit entry, and a warning in `fabricctl doctor` and the web UI until it is raised again. **No floor:** the command line can lower anything |

**Answered 2026-10-07 (owner), in 0.6.0:** reasoning in [5.8.1.27](../volume_5_notes_and_troubleshooting/5.8.1-samba-replaces-389ds.md#58127-before-060-uninstall-reinstall).

| # | Question | Decision |
|---|---|---|

## 1.2.6.5 Production from 0.6.1 (D113)

**Owner 2026-10-07:** 0.6.0's sign-in was too strict to be usable on the owner's network; 0.6.1 (1.1.4.6, the
0.6.x sign-in work) is that feedback fixed, and the first release the owner's home fabric runs for keeps.

| # | Question | Decision |
|---|---|---|
| D113 | When fabric has installs that must be kept (revises D101, D39, D37) | **0.6.1 is the first production release.** 0.6.0 may still be rebuilt. From 0.6.1 every release upgrades in place from the previous one (D39 in force), with the migrations it needs, and is tested that way: the previous release from apt `stable`, upgraded to the candidate from `testing`, then the host suite and a check that people, the CA, certificates, the domain, AdGuard's settings and secrets survived. Releases from 0.6.1 are full GitHub releases on apt `stable` (no longer pre-releases); candidates stay on `testing`. 1.0 remains the federation milestone |
