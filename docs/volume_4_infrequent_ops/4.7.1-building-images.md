# 4.7.1 Building fabric's images

Topics:

- 4.7.1.2 Building by hand

Status: **built 2026-10-03** (decision D41; proposal 5.1.4, D80–D83): the build matrix, the smoke test, the CI
build on both architectures and the signed publishing. Hosts still build these images themselves until they
use the published ones (the next step of 5.1.1.8).

## 4.7.1.1 What is built

Eight images, each for `linux/amd64` and `linux/arm64` (D29): `adguard`, `bind9`, `dirsrv`, `freeradius`,
`kea`, `keycloak`, `stepca` and `webui`. Their build files are in `packaging/images/<name>/`; a host installs the
same folders as `jinja/<name>/build/` (1.3.2), and `packaging/images/stage-contexts.sh` stages them from the
assembled tree so a published image is built from exactly what a host would build from (the web UI's with its app
in `app/`).

Every input is pinned: the bases by digest and Kea's package by version and signing key, all from
`config/images.lock.yaml` (`packaging/images/bake_env.py` prints them); no Dockerfile has a default base, so an
unpinned build fails at its `FROM`. The service account ids are the Dockerfiles' defaults (600–649, D42); a host
with other ids builds that image itself (P1, D80).

## 4.7.1.2 Building by hand

Any machine with Docker (global Rule 7.2). One image with a plain `docker build`:

```bash
bash packaging/images/stage-contexts.sh build/contexts
```

```bash
docker build --build-arg BASE_IMAGE="$(python3 packaging/images/bake_env.py | sed -n 's/^BASE_DEBIAN=//p')" -t fabric/bind9:local build/contexts/bind9
```

`bind9`, `dirsrv`, `freeradius`, `kea` and `webui` build FROM `BASE_DEBIAN`; `stepca`, `keycloak` and `adguard` FROM
`BASE_STEPCA`, `BASE_KEYCLOAK` and `BASE_ADGUARD`; `kea` also takes the `KEA_*` values, and `dirsrv` the
`BUILD_REV` in `packaging/docker-bake.hcl`. All eight at once, for this machine's platform:

```bash
bash -c 'set -a; . <(python3 packaging/images/bake_env.py); CONTEXTS=build/contexts; set +a; docker buildx bake -f packaging/docker-bake.hcl --load'
```

Then smoke test one: `bash packaging/images/smoke-test.sh bind9 ghcr.io/archdukejim/open-fabric/bind9:dev`. The
`images` suite (4.8.2) does all of this and checks the build inputs against a default host's compose files.

## 4.7.1.3 In CI

The `images` workflow (`.github/workflows/images.yml`) runs on every push and pull request that touches an image's
inputs: it builds the eight images on GitHub's native runners, `ubuntu-24.04` and `ubuntu-24.04-arm` (P3, D82: no
emulation), and smoke tests each one. The smoke test (`packaging/images/smoke-test.sh`) runs the image's program as
its service account with every capability dropped, no-new-privileges, a read-only root and no network, and checks
the labels hosts read (`org.fabric.base`, `org.fabric.ids`). Whether each service then works is proven by the
suites before a release (Rule 9; 4.8.2): `hardening`, `kea`, `freeradius`, `dirsrv`, `adguard` and the sandbox.

## 4.7.1.4 Publishing

Only from `main`, by hand: run the `images` workflow with **publish** ticked (Actions → images → Run workflow).

1. Each runner pushes its architecture as `<name>:<version>-amd64` / `-arm64` to
   `ghcr.io/archdukejim/open-fabric/<name>` (D38), with the repository's own token.
2. One job joins them into one multi-arch image, `<name>:<version>` (the version is `config/VERSION`), and signs
   its digest with cosign, keyless (P2, D81): the signer is the workflow's GitHub identity, recorded in Sigstore's
   public transparency log; there is no key to keep.
3. The run's summary lists each image's digest; they go into `config/images.lock.yaml` through a reviewed commit
   (D40) before the release is tagged.

The first publish creates the eight packages as private: make each **public** once in the repository's
Packages settings (P4, D83), so hosts pull without credentials.
