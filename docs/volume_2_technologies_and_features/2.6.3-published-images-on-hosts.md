## 2.6.3.1 What a host runs

fabric's eight own images (`adguard`, `bind9`, `freeradius`, `kea`, `keycloak`, `samba`, `stepca`, `webui`) are
pulled, pinned by digest, from `ghcr.io/archdukejim/open-fabric/<name>` (D38, D83) — exactly what CI built and
smoke tested. A host builds one of them itself only when it cannot use the published one:

- the lock has no published digest for it yet (a checkout or release before its first publish), or
- the host's service account ids differ from the ids baked into the published image (D80, D42).

Either way the host builds as before D41 (2.6.2: `FROM` the pinned base, `fabric/<name>:local`), so nothing changes
for it.

## 2.6.3.2 The lock's published section

`config/images.lock.yaml` gains a `published:` section beside `images:` and `packages:`:

```yaml
published:
  registry: ghcr.io/archdukejim/open-fabric
  # who may have signed them: the images workflow of this repository, from main, an rc/ branch or a v tag
  signer: ^https://github\.com/archdukejim/open-fabric/\.github/workflows/images\.yml@refs/(heads/main|heads/rc/.+|tags/v.+)$
  issuer: https://token.actions.githubusercontent.com
  images:
    bind9:   {var: image_fabric_bind9, tag: "", digest: "", account: bind, ids: "600:600"}
    ...
```

- `tag` and `digest` are empty until the first publish; a reviewed commit fills them (D40, 4.7.1.4).
- `account` names the service account (`service_users.<account>`) whose ids are baked in and `ids` those ids: the
  Dockerfile's defaults, which the `images` suite checks against the Dockerfiles and the defaults in
  `vars.yaml.j2`. stepca, keycloak and adguard bake none (no `account`).
- `vars.yaml.j2` sets `image_fabric_<name>` from it (the full `repo:tag@digest`, or "" when unpublished). Unlike the
  upstream images (2.6.2), these **follow the release**: they carry fabric's own code (the web UI's app, the
  directory's launcher), so a fabric upgrade moves them, as it rebuilt the local images before D41. An admin who
  must hold one lists its var in `image_pins`.
- The cosign image that verifies them is pinned in `images:` like any other (`image_cosign`, policy manual: D86).

## 2.6.3.3 Compose files and the local fallback

One rule, in one function (`fabriclib/images/published_image`), used by both the templates (a Jinja global) and
`fabricctl images`: an image's published ref is **in use** when `image_fabric_<name>` is set and the host's ids for
its account equal the published image's (or it has no account). Each of the eight compose templates then writes
either

- `image: <published ref>` and no `build:` section, or
- `image: fabric/<name>:local` with its `build:` section, as before.

Moving between them is an ordinary deploy: a changed `image:` line restarts the service (install_service_units).

## 2.6.3.4 Signature verification

Before a host uses a published digest for the first time — every deploy (setup, and `fabricctl images` moves, which
deploy) checks the refs it is about to run first — `fabriclib/images/verify_signature` runs `cosign verify` from the pinned cosign image,
requiring a keyless signature whose certificate names the signer and issuer of 2.6.3.2 (D81). A digest that
verified is remembered in `/etc/fabric/images/verified.json` (root, 0600), so it is checked once.

- **Refused** (D85): an unsigned image, a signature by anyone else, or a check that cannot run (no network to the
  registry or to Sigstore, an air-gapped host). The new digest is not used: setup stops before starting the service,
  and an update leaves the service on its current image.
- **The opt-out** (D85): `image_signature_check: false` in the host's vars turns the check off. It is a relaxation
  (global Rule 10): `fabricctl status` and the web UI's overview list it while it is set.
- Images the host builds itself are not signed and not checked: they are built from pinned inputs on the host.

## 2.6.3.5 `fabricctl images` with published images

`fabricctl images status` shows a published image in use as that service's image (var `image_fabric_<name>`,
running = the container's image, validated = the lock's ref). Setup moves them with the release (2.6.3.2), so
`images update` and `rollback` have nothing to do for them unless an admin holds one (`image_pins`; `update --force`
moves it back to the lock's). A service on its local build keeps the old behaviour (its var is its base). `prune`
counts the published repositories as fabric's, so old published digests are removed (never one in use or the
rollback one), and keeps the pinned cosign image.

## 2.6.3.6 Which refs publish, and promotion

Decision D84, an exception the owner made for this repository:

- **main and `rc/<version>` branches** publish by hand (the `images` workflow with *publish* ticked): main as
  `<version>`, an rc branch as `<version>-rc.<run number>`. Each publish is signed.
- **A `v<version>` tag** publishes `<version>` automatically by **promotion**: it builds nothing; it verifies the
  signatures of the digests the tagged commit's lock pins and tags those same digests `<version>`. A release thus
  runs exactly the images its release candidate tested, and the tag on the registry matches the release.

The release flow (4.7.1.4): branch `rc/<version>`, publish, pin the digests in the lock (reviewed commit on that
branch), run the suites and the sandbox against them, merge, tag.

## 2.6.3.7 Tests

The `images` suite (`tests/images/`, 4.8.2):

- `published.py` — rendered through the real templates: with the lock as it is, every compose file builds locally;
  with digests pinned, each names its published image and has no `build:` (and the Kea check uses it); custom ids
  for an account build that image locally again, leaving the others published; the lock's ids equal the
  Dockerfiles' and `vars.yaml.j2`'s defaults; the rule, `fabricctl images`' view of it and the relaxed-settings
  list.
- `verify.py` — against real keyless signatures in Sigstore's public log: cosign's own image verifies with its
  signer, is remembered (0600) and not checked again, and is refused with fabric's signer; an unsigned image, an
  unreachable registry and an unpinned ref are refused; the deploy step checks only images in use and nothing while
  the check is off.

The `sandbox`: with the lock pinning all eight, the core services run the published images (nothing built on the
host) and each was verified; before that, they are built on the host as before. `fabricctl status` lists the
relaxed settings (none).
