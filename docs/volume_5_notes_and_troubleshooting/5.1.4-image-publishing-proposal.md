Status: **approved by the owner on 2026-10-03, with P1–P4 as proposed** (D80–D83; global Rule 5.5: it changes D9,
D10 and D21). The owner decided C5 (D41) on 2026-10-03: "we will release a container package and

## 5.1.4.1 What changes

Today every host builds eight images itself, from a pinned base and Debian packages: `adguard`, `bind9`,
`dirsrv`, `freeradius`, `kea`, `keycloak`, `stepca` and the web UI (`fabric-web`). That costs the Pi time and
memory at setup, makes hosts differ (each installs whatever packages the archive had that day) and needs the
network at build time. With D41 they are built once, in CI, tested, published and pinned by digest like every
other image; hosts only pull them.

## 5.1.4.2 How it works

- **Packaging:** each image's Dockerfile and build files in `packaging/images/<name>/` (5.1.3); code that runs
  inside it stays in `src/containers/<name>/`. One build matrix, `packaging/docker-bake.hcl`, lists the eight
  images × amd64 and arm64 (D29). Each also builds with a plain `docker build` (global Rule 7.2), documented in
  Volume 4.
- **Publishing:** GitHub Actions builds the matrix on every release and when a base image changes (the watcher
  of 2.6.2), runs a smoke test per image (it starts and reports healthy), and pushes multi-arch images to the
  GitHub Container Registry (`ghcr.io/archdukejim/open-fabric/<name>`, D38), tagged with fabric's version.
- **Pinning:** the published digests go into `images.lock.yaml` through a reviewed commit (D40, D21), so a host
  runs exactly what CI tested.
- **Hosts:** compose files name the pinned image instead of a `build:` section; setup pulls; `fabricctl images
  update` (3.11.1) keeps managing updates and rollbacks. Offline installs carry the images in the bundle (D45).

## 5.1.4.3 Decisions needed

| # | Question | Proposal |
|---|---|---|
| P1 | Images bake their service account's ids (e.g. `DS_UID`); a published image has the defaults (600–649, D42). What happens on a host that changed them? | The host builds that one image locally, as today (the build files ship in the package): published images for default ids, a local build only for custom ones |
| P2 | Sign the published images? | Yes: keyless signing in GitHub Actions (cosign with GitHub's OIDC identity); hosts verify the signature before using a new digest |
| P3 | Build arm64 how? | GitHub's native arm64 runners (free for public repositories) — no emulation, the same speed as amd64 |
| P4 | Public or private images? | Public, like the repository: hosts pull without credentials |

## 5.1.4.4 Impact assessment

- **Architecture:** D9 (fabric updater, local registry) and D10 (a signed channel on GitHub Pages) are replaced
  by the registry and the lock file; D21's pipeline gains the build and publish steps. Hosts no longer build
  images except for custom ids (P1).
- **Breaking changes:** an existing install switches from its locally built image to the published one at its
  next `fabricctl images update` or setup (same image content, different digest); the rollback record keeps the
  local one until pruned. CI needs package-write permission to GHCR.
- **Scope creep risk:** medium: the CI pipeline (watcher, regression, issues) of 2.6.2 is larger than this; only
  build, smoke test, sign, publish and the lock update are in scope here.

## 5.1.4.5 Follow-up decisions D84–D86

Asked while designing the host side (2.6.3) on 2026-10-03; the owner chose:

- **D84, which refs publish.** Publishing only from main would leave no way to test hosts against fabric's own
  signed images before a merge, and a release would rebuild images nobody tested. The owner made an exception:
  release-candidate branches (`rc/<version>`) publish too, and a release tag promotes the candidate's digests instead
  of rebuilding (2.6.3.6). Rejected: publishing from any branch (unreviewed images in the public registry).
- **D85, an unverifiable signature.** Refusing keeps D81 meaningful: a check that silently passes when it cannot run
  protects nothing. Air-gapped hosts turn it off explicitly, and the relaxation is visible (Rule 10). Rejected:
  warn and continue (weakens D81 silently); verify only when pinning (would change D81).
- **D86, running cosign.** Ubuntu 24.04's archive has no cosign; a pinned image needs nothing installed on the host
  and is updated like every other image. Rejected: a host package from GitHub releases (a second pin and update
  path).
