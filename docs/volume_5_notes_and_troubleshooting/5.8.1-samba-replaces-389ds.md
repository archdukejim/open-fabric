The owner's answers to the Samba decisions (1.2.6), 2026-10-04:

- **S1 (D73), where passwords and people live:** "If we can replace 389-DS with Samba I think we should and simplify
  the container stack." Samba AD becomes fabric's one directory; 389-DS goes.
- **S2 (D74), site controllers:** the owner asked for "federated levels": a site's admins change only their site,
  while the configuration replicates everywhere. AD's answer within one domain: an organisational unit (OU) per
  site with rights delegated to that site's admins; schema, configuration and Group Policy replicate to every
  controller; read-only controllers (RODCs) where the spike proves them. A forest of several domains (true
  per-site domains) is, as far as is known, not supported by Samba; the spike confirms it.
- **S3 (D75), the controller's address:** the host's address. Ports 389/636 are free once 389-DS is gone; BIND
  keeps 53 and serves the AD zone through Samba's DLZ plugin.
- **S4 (D76), Linux joins:** follows S1 (there is only AD to join); the owner confirms it with the rewritten
  design.
- S5 (D77) and S6 (D78): not yet answered.

## 5.8.1.2 What changes

Today 389-DS is fabric's directory: people, groups, POSIX ids, devices and their roles, the address plan, split
into an organisation part and site parts and replicated between sites (M1, M1b, M5). Samba AD would take all of
that over and add what only AD gives: Windows logons and Group Policy, Kerberos single sign-on for Linux,
PEAP-MSCHAPv2 for 802.1X, one password store. The stack loses a container (`dirsrv`) and a replication system
(fabric's own agreements and `fabric-directory-sync`), and the hardest part of the old Samba design — keeping
passwords equal in two directories — disappears.

## 5.8.1.3 What replaces what

| Today (389-DS) | With Samba AD |
|---|---|
| `dirsrv` container, `ldap_base_dn`, organisation suffix + `ou=<site>` sub-suffixes (M1, M1b) | `samba` container (a DC), realm `AD.<DOMAIN>`; the organisation's objects in the domain, one OU per site |
| M5 replication: agreements, read-only organisation at sites, `fabric-directory-sync.timer` | AD replication between the site DCs; AD sites built from the address plan; RODCs at sites if proven |
| fabric's schema (`05-schema.ldif`: 15 attributes and classes for devices, device roles, networks, sites) | The same attributes added to AD's schema (permanent once added) or kept as fabric data elsewhere — decided by the spike |
| ACIs and fabric's service accounts (`30-aci.ldif`, `20-accounts.ldif`) | AD ACLs on OUs (`samba-tool dsacl`), delegated per site; service accounts as AD users |
| Keycloak federates to 389-DS (writable) | Keycloak federates to AD (its LDAP provider in AD mode; passwords checked by AD) |
| FreeRADIUS looks devices and people up in 389-DS; EAP-TTLS checks passwords by LDAP bind | FreeRADIUS looks up in AD; PEAP-MSCHAPv2 through `ntlm_auth` (winbind); EAP-TLS unchanged |
| Linux clients: SSSD against 389-DS (M10 steps 1–3) | Linux clients join AD (`realm join`, Kerberos); sudo rules in AD (the sudo schema) |
| POSIX ids from fabric (`ensure_posix_identities`) | RFC 2307 attributes in AD (`--use-rfc2307`), assigned by fabric as today |
| The web UI's directory pages and fabric-agent through `fabriclib/ldap` | The same pages and routes through a directory layer that speaks to AD |
| Address plan stored in the directory (M8) | In AD (schema) or in fabric's own data, replicated with it — decided by the spike |
| BIND only; AD DNS behind it (old design, macvlan) | BIND serves fabric's zones and, through DLZ, the AD zone; Windows registers its names by signed dynamic updates |

## 5.8.1.4 Impact assessment

**Architecture.** The directory moves from 389-DS to Samba AD everywhere. 1.3 (topology), 1.5 (agent API), 1.8
(federation: M1, M1b, M5), 2.2.2.6 (address plan), 2.10.1 (Linux join), 2.11.1 (Samba) and the container
inventory (1.3.8, D49) are rewritten. Keycloak, FreeRADIUS, BIND, Step-CA and OpenBao stay; their links to the
directory change. The core-services rule (1.9.1: DNS, DHCP, LDAP, SSO and nginx never depend on OpenBao to start)
applies to the DC as it did to 389-DS.

**Breaking changes.**

- Every existing install migrates once: people, groups, POSIX ids, devices, device roles and the address plan
  move from 389-DS to AD; **passwords cannot move** (389-DS keeps only one-way hashes), so every person sets a new
  password at the first sign-in after the upgrade (Keycloak's required action). Installs are few (the owner's
  two houses and test machines), so a guided migration plus that one reset is proposed.
- Federation: sites join the AD domain instead of a 389-DS replica; the invitation carries what a DC needs to join.
  Existing sites re-join.
- The fabric-agent routes for people, devices and roles keep their shape; their backend changes.
- The memory budget at 4 GB changes (a DC instead of 389-DS; measured in the spike).
- The host publishes the DC's ports (88, 135, 389, 445, 464, 636, 3268/3269, the RPC range): a host change that
  goes through consent (2.7.1).

**Scope creep risk: high.** It touches most of fabric. Contained by: the spike first (5.8.1.5) — if a question
fails, the replacement stops and the old design (Samba beside 389-DS) is the fallback; then one rewritten design
approved before any code; then the build in steps, each tested, with 389-DS kept running until the AD side passes
the same suites (dirsrv, keycloak, freeradius, federation, sandbox).

## 5.8.1.9 Outcome of the spike

**Every question passes.** Samba AD can replace 389-DS as fabric's directory, built from Debian's packages on
fabric's base, hardened like the other containers. What the rewritten design must carry (each from a result above):

- The DC runs with CHOWN, DAC_OVERRIDE, FOWNER, SETUID and SETGID — no others (SETGID and SETUID alone serve
  sign-ins, but Group Policy writes ACLs on SYSVOL; Q16),
  read-only, its full host name, its sockets on `/run`; provisioning output discarded (it prints a temporary
  password); the administrator's password set from a file.
- BIND gains Samba's DLZ module (`samba-libs`, `samba-dsdb-modules`), the DC's `smb.conf` read-only, the DC's
  `bind-dns` folder and a writable `/var/tmp`; its limit goes to 128 MiB.
- fabric's schema moves to an AD-valid OID arc derived from its UUID, loaded in two sessions; structural classes
  carry a default security descriptor.
- Sites are OUs in one domain with delegated rights (Samba has no child domains); RODCs work (Kerberos forwarded,
  cached sign-ins with the root DC down, writes refused); NTLM forwarding at an RODC is tested again in S1.
- Keycloak federates to AD (writable, LDAPS); fabric decides the old-password window (60 minutes by default).
- FreeRADIUS uses the DC's winbind for PEAP (`ntlm auth = mschapv2-and-ntlmv2-only` in `smb.conf`, the
  privileged folder in its group); EAP-TLS unchanged.
- Linux machines join with adcli into their site's OU; SSSD gives fabric's ids, access by group and sudo from AD
  (sudo's schema with its own OIDs).
- Migration moves everything but passwords and 389-DS's service accounts; people set a new password once.

The owner now approves or rejects the replacement (5.8.1.6); on approval the designs of 5.8.1.4 are rewritten.

## 5.8.1.10 Owner decisions after the first runs, and Q12–Q16

On 2026-10-04, after Q1–Q11, the owner answered S5 and S6, revised S2 and added D87–D90 (register: 1.2.6): the AD
domain is chosen at setup (`ad.<domain>` recommended for federation, fabric's own domain acceptable for one
location, permanent); everything fabric manages lives under `OU=sites`; Group Policy pushes only the trusts fabric
needs, the rest through an ADMX-driven editor; the DC's certificates come from Step-CA; the password policy is the
admin's, with no defaults; each site chooses and can change its DC type, site DCs are independent and resync, each
writes only its own site by default; access is authorized per site. The owner asked for Q12–Q16 (5.8.1.5) before
these go into the rewritten design; the replacement itself still waits for approval on the results.

| # | Result | Findings |
|---|---|---|
| Q12 | **Pass** | A writable site DC joins and is cut off from the root while its site's LAN still reaches it. While cut off: the site admin adds a person to its own site at the site DC, and is still refused in another site (ACLs are checked by every DC, offline too); the root adds a person elsewhere. After reconnecting, both DCs have both sides' changes; the same attribute changed on both sides converged to the later write on both; the same new name created on both sides kept both objects, one renamed (`CNF:`), nothing lost. | Q15 | **Pass** | A site DC goes writable → read-only → writable by demoting it and joining again under the same name; each time it gets its site's data again, and one account remains (no leftovers). | Q16 | **Pass** | A GPO on house2's OU grants log-on (local and remote) to `house2-users` only; a house2 Linux machine enforces it through SSSD (`access_provider = ad`, `ad_gpo_access_control = enforcing`): a house2 person may log on, a house1 person is refused; explicitly allowed, the house1 person may; with the blanket policy (Domain Users) anyone in the organisation may. ## 5.8.1.12 Findings while building S1

Recorded as S1 is built (2026-10-04, manual 2.11.2.15); each is in the code and the `samba` suite:

- **Q6 follow-up settled:** an RODC forwards NTLM sign-ins for accounts it does not cache to a writable DC (fabric's
  image, `smb.conf` with `ntlm auth = mschapv2-and-ntlmv2-only`). With the writable DC down, only cached people sign
  in, the Administrator is refused and writes are refused. RODC about 216 MiB of 512.
- **The DC needs `nsupdate`** (`bind9-dnsutils`): `samba_dnsupdate` registers the DC's names through BIND with it.
  The spike's image had it by chance; without it a DC's records are never written.
- **A failed provisioning leaves `sam.ldb` behind**, which a later start took for a domain: fabric marks a domain
  provisioned only on success (`.fabric-provisioned`) and clears a failed attempt, keeping the folders BIND mounts.
- **Provisioning with BIND9_DLZ needs `tdbbackup`** (`tdb-tools`).
- **BIND must share the DC's address** for signed updates: the AD zone sends members' updates to the DC's name. On an
  install both use the host's address (D98); the test runs BIND in the DC's network namespace.
