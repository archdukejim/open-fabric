- **S1 (D73), where passwords and people live:** "If we can replace 389-DS with Samba I think we should and simplify

- **S3 (D75), the controller's address:** the host's address. Ports 389/636 are free once 389-DS is gone; BIND

- **S4 (D76), Linux joins:** follows S1 (there is only AD to join); the owner confirms it with the rewritten
  design.
- S5 (D77) and S6 (D78): not yet answered.

## 5.8.1.2 What changes

Today 389-DS is fabric's directory: people, groups, POSIX ids, devices and their roles, the address plan, split
into an organisation part and site parts and replicated between sites (M1, M1b, M5). Samba AD would take all of
that over and add what only AD gives: Windows logons and Group Policy, Kerberos single sign-on for Linux,
PEAP-MSCHAPv2 for 802.1X, one password store. The stack loses a container (`dirsrv`) and a replication system
(fabric's own agreements and `fabric-directory-sync`), and the hardest part of the old Samba design — keeping
passwords equal in two directories — disappears.

## 5.8.1.3 What replaces what

| Today (389-DS) | With Samba AD |
|---|---|
| `dirsrv` container, `ldap_base_dn`, organisation suffix + `ou=<site>` sub-suffixes (M1, M1b) | `samba` container (a DC), realm `AD.<DOMAIN>`; the organisation's objects in the domain, one OU per site |
| M5 replication: agreements, read-only organisation at sites, `fabric-directory-sync.timer` | AD replication between the site DCs; AD sites built from the address plan; RODCs at sites if proven |
| fabric's schema (`05-schema.ldif`: 15 attributes and classes for devices, device roles, networks, sites) | The same attributes added to AD's schema (permanent once added) or kept as fabric data elsewhere — decided by the spike |
| ACIs and fabric's service accounts (`30-aci.ldif`, `20-accounts.ldif`) | AD ACLs on OUs (`samba-tool dsacl`), delegated per site; service accounts as AD users |
| Keycloak federates to 389-DS (writable) | Keycloak federates to AD (its LDAP provider in AD mode; passwords checked by AD) |
| FreeRADIUS looks devices and people up in 389-DS; EAP-TTLS checks passwords by LDAP bind | FreeRADIUS looks up in AD; PEAP-MSCHAPv2 through `ntlm_auth` (winbind); EAP-TLS unchanged |
| Linux clients: SSSD against 389-DS (M10 steps 1–3) | Linux clients join AD (`realm join`, Kerberos); sudo rules in AD (the sudo schema) |
| POSIX ids from fabric (`ensure_posix_identities`) | RFC 2307 attributes in AD (`--use-rfc2307`), assigned by fabric as today |
| The web UI's directory pages and fabric-agent through `fabriclib/ldap` | The same pages and routes through a directory layer that speaks to AD |
| Address plan stored in the directory (M8) | In AD (schema) or in fabric's own data, replicated with it — decided by the spike |
| BIND only; AD DNS behind it (old design, macvlan) | BIND serves fabric's zones and, through DLZ, the AD zone; Windows registers its names by signed dynamic updates |

## 5.8.1.4 Impact assessment

**Architecture.** The directory moves from 389-DS to Samba AD everywhere. 1.3 (topology), 1.5 (agent API), 1.8
(federation: M1, M1b, M5), 2.2.2.6 (address plan), 2.10.1 (Linux join), 2.11.1 (Samba) and the container
inventory (1.3.8, D49) are rewritten. Keycloak, FreeRADIUS, BIND, Step-CA and OpenBao stay; their links to the
directory change. The core-services rule (1.9.1: DNS, DHCP, LDAP, SSO and nginx never depend on OpenBao to start)
applies to the DC as it did to 389-DS.

**Breaking changes.**

- Every existing install migrates once: people, groups, POSIX ids, devices, device roles and the address plan
  move from 389-DS to AD; **passwords cannot move** (389-DS keeps only one-way hashes), so every person sets a new
  password at the first sign-in after the upgrade (Keycloak's required action). Installs are few (the owner's
  two houses and test machines), so a guided migration plus that one reset is proposed.
- Federation: sites join the AD domain instead of a 389-DS replica; the invitation carries what a DC needs to join.
  Existing sites re-join.
- The fabric-agent routes for people, devices and roles keep their shape; their backend changes.
- The memory budget at 4 GB changes (a DC instead of 389-DS; measured in the spike).
- The host publishes the DC's ports (88, 135, 389, 445, 464, 636, 3268/3269, the RPC range): a host change that
  goes through consent (2.7.1).

**Scope creep risk: high.** It touches most of fabric. Contained by: the spike first (5.8.1.5) — if a question
fails, the replacement stops and the old design (Samba beside 389-DS) is the fallback; then one rewritten design
approved before any code; then the build in steps, each tested, with 389-DS kept running until the AD side passes
the same suites (dirsrv, keycloak, freeradius, federation, sandbox).

## 5.8.1.9 Outcome of the spike

**Every question passes.** Samba AD can replace 389-DS as fabric's directory, built from Debian's packages on
fabric's base, hardened like the other containers. What the rewritten design must carry (each from a result above):

- The DC runs with CHOWN, DAC_OVERRIDE, FOWNER, SETUID and SETGID — no others (SETGID and SETUID alone serve
  sign-ins, but Group Policy writes ACLs on SYSVOL; Q16),
  read-only, its full host name, its sockets on `/run`; provisioning output discarded (it prints a temporary
  password); the administrator's password set from a file.
- BIND gains Samba's DLZ module (`samba-libs`, `samba-dsdb-modules`), the DC's `smb.conf` read-only, the DC's
  `bind-dns` folder and a writable `/var/tmp`; its limit goes to 128 MiB.
- fabric's schema moves to an AD-valid OID arc derived from its UUID, loaded in two sessions; structural classes
  carry a default security descriptor.
- Sites are OUs in one domain with delegated rights (Samba has no child domains); RODCs work (Kerberos forwarded,
  cached sign-ins with the root DC down, writes refused); NTLM forwarding at an RODC is tested again in S1.
- Keycloak federates to AD (writable, LDAPS); fabric decides the old-password window (60 minutes by default).
- FreeRADIUS uses the DC's winbind for PEAP (`ntlm auth = mschapv2-and-ntlmv2-only` in `smb.conf`, the
  privileged folder in its group); EAP-TLS unchanged.
- Linux machines join with adcli into their site's OU; SSSD gives fabric's ids, access by group and sudo from AD
  (sudo's schema with its own OIDs).
- Migration moves everything but passwords and 389-DS's service accounts; people set a new password once.

The owner now approves or rejects the replacement (5.8.1.6); on approval the designs of 5.8.1.4 are rewritten.

## 5.8.1.10 Owner decisions after the first runs, and Q12–Q16

On 2026-10-04, after Q1–Q11, the owner answered S5 and S6, revised S2 and added D87–D90 (register: 1.2.6): the AD
domain is chosen at setup (`ad.<domain>` recommended for federation, fabric's own domain acceptable for one
location, permanent); everything fabric manages lives under `OU=sites`; Group Policy pushes only the trusts fabric
needs, the rest through an ADMX-driven editor; the DC's certificates come from Step-CA; the password policy is the
admin's, with no defaults; each site chooses and can change its DC type, site DCs are independent and resync, each
writes only its own site by default; access is authorized per site. The owner asked for Q12–Q16 (5.8.1.5) before
these go into the rewritten design; the replacement itself still waits for approval on the results.

| # | Result | Findings |
|---|---|---|
| Q12 | **Pass** | A writable site DC joins and is cut off from the root while its site's LAN still reaches it. While cut off: the site admin adds a person to its own site at the site DC, and is still refused in another site (ACLs are checked by every DC, offline too); the root adds a person elsewhere. After reconnecting, both DCs have both sides' changes; the same attribute changed on both sides converged to the later write on both; the same new name created on both sides kept both objects, one renamed (`CNF:`), nothing lost. ## 5.8.1.12 Findings while building S1

Recorded as S1 is built (2026-10-04, manual 2.11.2.15); each is in the code and the `samba` suite:

- **Q6 follow-up settled:** an RODC forwards NTLM sign-ins for accounts it does not cache to a writable DC (fabric's
  image, `smb.conf` with `ntlm auth = mschapv2-and-ntlmv2-only`). With the writable DC down, only cached people sign
  in, the Administrator is refused and writes are refused. RODC about 216 MiB of 512.
- **The DC needs `nsupdate`** (`bind9-dnsutils`): `samba_dnsupdate` registers the DC's names through BIND with it.
  The spike's image had it by chance; without it a DC's records are never written.
- **A failed provisioning leaves `sam.ldb` behind**, which a later start took for a domain: fabric marks a domain
  provisioned only on success (`.fabric-provisioned`) and clears a failed attempt, keeping the folders BIND mounts.
- **Provisioning with BIND9_DLZ needs `tdbbackup`** (`tdb-tools`).
- **BIND must share the DC's address** for signed updates: the AD zone sends members' updates to the DC's name. On an
  install both use the host's address (D98); the test runs BIND in the DC's network namespace.
- **GPOs can be made locally** on the DC's own database and SYSVOL, without SMB or credentials, as samba-tool makes
  them over the network: the converge code needs no Administrator password.
- **The host-network DC needs NET_BIND_SERVICE** (test Pi): Docker's unprivileged low ports apply only inside a
  container's own network namespace, so on the host's the DC could bind none of 88, 135, 389, 445, 464, 636. The
  owner added the capability (D49's inventory, 1.3.9); NetBIOS is off, so nothing binds 137.
- **The DC's data folder must be traversable** (host-1's first Group Policy run): the DC serves SYSVOL as each
  user (it switches identity), and fabric had made `/opt/samba/data` 0700, so every machine was refused its GPOs.
  It is 0755 now (Samba keeps `private/` 0700, SYSVOL under its ACLs); the suite reads SYSVOL as a domain user.
- **The DC needs its own resolver** (test Pi, `use_host_dns`): in the host network it used the host's resolver,
  which does not know the AD zone, so it could not find its own KDC; fabric mounts a `resolv.conf` naming the host's
  address.
- **A host copies image build folders with plain modes**: the DC's entrypoint lost its execute bit on the Pi
  (WSL's Windows drive hid it); the Dockerfile sets it.
- **A joined machine's local Administrators** must stay in the site's log-on policy, which replaces Windows'
  local lists.
- **ACL entries must be compared parsed**: Samba rewrites SDDL text, so a text comparison would add an entry again on
  every run.

## 5.8.1.16 S3: FreeRADIUS on AD

Findings while moving FreeRADIUS to AD (S3.2, 2026-10-05), all covered by the `freeradius` suite against a real DC:

- **AD has its own groups with common names** (`Guests`, `Users`, `Administrators`, in `CN=Builtin`), and group
  names are unique across the domain: a fabric group called `guests` cannot be made, and a `radius_people` mapping
  of `guests` would have matched AD's own group. The person check therefore only takes groups under `OU=sites`
  (fabric's), plus Domain Users (`users`) from the primary group, which `memberOf` never lists.
- **AD answers every refused bind alike** (`invalidCredentials`, with the reason only in a diagnostic code): a wrong
  password, a locked, disabled or expired account and a one-time password not yet changed are all "wrong password or
  account locked" in the auth log. A person on their one-time password sets their own at the web sign-in first.
- **Roles are read only from the site's own `OU=device-roles` and the organisation's**, by FreeRADIUS and by the
  web UI alike: another site's role of the same name never grants anything here.
- FreeRADIUS no longer needs `install_ldap`: the DC is part of every install.

**D102 (owner, 2026-10-05): PEAP machine sign-in uses the group mappings.** Asked before S3.3 because the design
named PEAP for machines without saying which machines get in. Options put to the owner: the `radius_people`
mappings for machines too (chosen); every enabled machine of the site on the port's default VLAN (no control, no
off switch); or a fabric device per machine whose roles grant a new permission (most control, but a device record
for every joined machine and a new permission in the vocabulary). The mappings reuse one mechanism and one screen,
give machines a VLAN, and admit no machine until a group is mapped.

S3.3 (PEAP, 2026-10-05), built as the spike found (Q8): FreeRADIUS asks the DC through its own winbind, with no
member join. Findings:

- The DC's winbind sockets go through a host folder (`<deploy_base>/samba/winbindd`, mounted over the DC's `/run`
  tmpfs), and its privileged pipe lives in its data folder; converge puts that folder in FreeRADIUS's group (root,
  0750) after every start. FreeRADIUS mounts the DC's `etc/` folder rather than `smb.conf` alone: the DC's entrypoint
  rewrites the file (a new inode), which a single-file mount would not follow.
- `%{mschap:User-Name}` already turns a machine's `host/ws1.<domain>` into `ws1$` (and `DOMAIN\alice` into
  `alice`): the spike's own rewrite is not needed.
- The policy decides PEAP in the inner tunnel's post-auth, once the domain has accepted the answer: the account
  must then be in a mapped group (D102); a machine also in the site's `OU=machines`.
- FreeRADIUS's `%{%{…}:-…}` expansions are Jinja tags to the renderer: `mods/mschap` is rendered raw.

## 5.8.1.18 S6: Linux machines on AD

## 5.8.1.20 S8: sites joining the root's domain

Built 2026-10-05 (2.11.2.22 S8.1–S8.3); `tests/samba/site_join.py` joins a writable and a read-only site DC to a root DC
with BIND serving the AD zone. Findings:

- **A joining DC resolves through the root.** Its own host's BIND has no AD zone before it joins, so its resolver
  points at the root's address until it has (deploy_samba), then at its own host as at the root.
- **Replication back to the root needs a site link.** A new AD site in no site link left the root with an inbound
  neighbour it never pulled from. Convergence keeps one link per site to its parent (cost 100, 15 minutes, change
  notification on); AD's KCC then builds the return path within its 5-minute round.
- **SYSVOL's files are not at a joined DC** (D94's subject): the domain's own GPO folders are missing there, so
  `samba-tool ntacl sysvolreset` fails. fabric now sets each GPO folder's ACLs from its object as it writes it, as
  Samba's provisioning does per GPO; S8.4 brings the other sites' folders.
- **The join account is a Domain Admin**, as Samba's DC join requires by default; it expires one hour after the root
  makes it and is deleted once the site joined. Whether less is enough (1.8.8.4) is not established yet.
- An RODC's convergence touches only what is local (winbind's pipe); its site's objects are made by the root, and
  writes at it are refused.
- Sites nested under a site and sites with no DC do not join the domain yet: how they write through the root is to be
  designed with the owner (S8.8).


## 5.8.1.21 The owner's S8 answers

2026-10-05, on the questions S8.1–S8.5 left open:

- **SYSVOL (D94 revised).** The owner asked whether the shares would be small, lasting, and could go over HTTPS.
  Every DC shares SYSVOL and NETLOGON over SMB for its own Windows machines whatever DCs use between themselves, so
  no share is added; GPO folders are a few KB (the template store a few MB, once), copied for as long as anyone
  edits policy. HTTPS through nginx was possible (D94 as recorded) but needs the endpoint's mutual-TLS routes,
  which do not exist yet; SMB with the DCs' machine accounts needs no new port and no new authentication. The
  owner accepted SMB **on the condition that SYSVOL is never advertised**: Windows lists what it discovers, and
  fabric never wants its shares populated there. NetBIOS was already off and the container runs no WS-Discovery;
  the shares are made not browseable and mDNS is turned off explicitly. Whether Windows still applies policy with
  the shares hidden is one of the owner's Windows checks (5.8.1.19).
- **Overrides and grants (D104).** The owner prefers a database to files, for fabric's scale later, and Postgres.
  The owner then asked for it to be at every site and kept in sync. Postgres's own logical replication with one
  writer per row was chosen over pulling copies through the endpoint (slower, and code of our own) and over
  keeping the records in AD (replicated already, but the owner prefers a database). The owner preferred not to
  expose Postgres: compared were Postgres on a host port (its own pre-authentication code facing the linked sites)
  and nginx in front (nothing reaches Postgres without a valid site certificate); nginx was chosen, with TLS
  inside as well, which D51 requires anyway. To prove before building: Postgres 17+'s direct TLS
  (`sslnegotiation=direct`) through nginx's stream TLS, and TLS again from nginx to Postgres. Routing it through 443
  by name (no new port) was set aside: it means restructuring every HTTPS server in nginx.
- **Nesting (D105).** The owner's model: a site sits in an OU under its parent and inherits its parent's settings
  by default, unless overridden with explicit settings or with inheritance disabled; the same from the domain
  level. This is AD's own GPO and ACL inheritance, so the flat layout of 1.8.8.6 (kept from M1b) was replaced. A
  parent's controls that its children may not change are enforced links, which also reconciles D103's "may not
  override set controls from the parent site" with a child's right to block inheritance. Cost: code that assumed
  `OU=<site>,OU=sites` (60 places in 39 files) and subtree searches from a site's OU, which would take in its
  children; re-parenting becomes an OU move. No user is affected (D101).
- **Roles (D103).** The owner: site admins get sudo across the site's devices, may add devices and adjust the
  site's GPOs, may not override the parent's controls, and each of these is a role that may be given to a different
  admin group; Windows local administration is a role of its own, as is managing the OU. A parent's roles reach its
  children by default (owner, yes).
- **Test boxes.** The owner allows wiping host-1, host-2 and the test Pi, and their test domains, for development
  and testing, asked before each time as for S8.9.

## 5.8.1.22 S8.4: Group Policy between sites over SMB

Built 2026-10-05 (1.8.8.15); `tests/samba/site_join.py` proves it with a root, a writable and a read-only site DC:
SYSVOL and NETLOGON are left out of a share list yet open by their path, every DC ends with every GPO's folder at
its object's version (the root's from the root, the writable site's from its own DC, the read-only site's from the

- **Which site is the root** cannot be read from where an OU sits while sites are flat (every site's OU is right

- The DC's entrypoint runs the pull 60 seconds after start and every 5 minutes after; one pull at a time (a lock in

## 5.8.1.23 S8.8: sites nest in the directory

The first part of S8.8 (D105, 1.8.8.14), built 2026-10-05: a site's OU is made in its parent's and marked as a site OU
(`fabricSiteInfo`, the class that also carries its id block), and found by that mark and its name everywhere
(`paths.site_dn`), never built from `OU=sites`. Tested in `tests/samba/dc.py` (a parent's agent writes in the site
below it; a nested site's agent and admin are refused in the parent, on the nested site's service accounts, and
changing their OU's permissions, against a control where the domain's Administrator makes the same change),
`site_join.py` (both site DCs nested under the root, joined and replicating), `linux_join.py` (the installer finds
its site's OU with Kerberos and LDAP), and the federation, FreeRADIUS and Keycloak suites. Findings:

- **Rights to change permissions were removed** from the site's admins and agent (`WD`, `WO`): with them a nested
  site could protect its OU and shut its parents out. Nothing fabric does needs them as a person or the agent;
  convergence sets ACLs as the system.
- **A parent's principals are denied on a nested site's service accounts** explicitly (an explicit deny is
  evaluated before an inherited allow).
- **Which site is the root** is the one whose OU holds `OU=organisation`, as for S8.4.
- Hosts keep the site's place as `ad_site_ou` and `ad_org_ou` (from the join); this also fixed Keycloak's group
  mapper at a site that is not the root, which looked for the organisation's groups in the site's own OU.
- The Linux installer reads its site's place from the DC before it joins (`kinit` as the joining account, then a
  GSSAPI search); SSSD reads sudo rules one level deep from the site's `OU=sudoers`, each one above it and the
  organisation's, which also closes the gap that organisation-wide rules did not reach other sites.
- **Controls** (built the same day): each site's `fabric: <site> controls` GPO, linked enforced (`gPLink` option 2),
  set with `fabricctl gpo set … --control` or the web UI's *As a control (enforced)*; `tests/samba/gpo.py` proves the
  link options and that the admin settings keep their own value. That a Windows machine of a nested site applies
  its parent's control over its own setting is a Windows check for the two-site setup (S8.9).
- **Invitations made by a nested parent** (built the same day): any site with a writable DC names the domain in its
  invitations and prepares the new site in its own DC, inside its OU; the next id block is the one after every block
  the domain holds (`read_id_blocks.py`), so a parent that knows only its own children never repeats another
  branch's. `site_join.py` now runs four DCs: lab (under the root) prepares lab2, which joins through lab's DC and
  BIND; lab2's person reaches the root two levels up, and lab's agent resets it (inherited rights).
- **A DC that has just joined may have no RID pool yet**: lab2's first request to the RID master (the root) failed
  and was retried 15 s later, and until then its agent's new accounts were refused as an access error. SMB copies
  from the parent's DC also failed once in the first minutes, then worked (5.4.2).
- Still open in S8.8 (asked of the owner): whether a site may have no DC at all.
