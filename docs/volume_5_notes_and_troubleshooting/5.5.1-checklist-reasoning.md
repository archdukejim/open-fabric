## 5.5.1.1 Product shape (D26–D31)

fabric exists to set up and run a network's core services on a host, so it is a host product (D26). The owner
framed it as two products from the start, the `fabricctl` control and the Open Fabric web control (D14), which
Rule 7.2 calls two UX variants; they share one package because the web UI is only a client of the agent the
package installs (D27). Ubuntu LTS is what the reference Raspberry Pi and the test machines run (D28). On 2026-10-04 the owner made it the
only host target, dropping Debian 13 and Raspberry Pi OS from D2: one large, widely supported distribution with a
long support cycle, backed by one of the largest groups, rather than a test matrix spread over three. The owner
requires arm64 for the Pi and amd64 for testing (D29). There is no commercial edition (D30). The 4 GB Pi budget
shaped every memory limit (D31).

## 5.5.1.2 Code and repository (D32–D36)

Python was chosen over Go so the package needs no build step and hosts can read what runs (D1, D32). One package
is enough for one product (D33). ruff and shellcheck catch real errors in the code as written; a typecheck would
need annotations the code does not carry, so it waits (D34, owner: "whatever you recommend"). The repository is
on GitHub and already builds in Actions (D35). The structured docstrings and the generated reference were the
owner's choice on 2026-09-28 and are built (D36).

## 5.5.1.3 Release and packaging (D37–D41)

`config/VERSION` already follows semantic versioning (D37). Releases already publish the `.deb` (D7, D38). Only
the previous release must upgrade, because the owner rebuilds older installs instead of migrating them (D39).
Digest pinning keeps an upstream push from changing what runs (D21, D40). Building images on each host costs the
Pi time and makes hosts differ; the owner chose to publish fabric's own images and manage their updates (D41,
2026-10-03).

## 5.5.1.4 Installed footprint (D42–D46)

The `fabric-*` names and the 600–649 band avoid Ubuntu's own accounts after the 26.04 upgrade asked to remove
`bind` (D42). Every install already uses `/opt`, which D3 had wanted to change (D43). Uninstall exports on request
because it removes the CA and the vault; downloaded images are kept because they are large and shared (D44). The
owner insisted that offline must always work (D45). The host-change groups are the consent design (D46, 2.7).

## 5.5.1.5 Security (D47–D51)

OpenBao holds secrets so nothing sensitive sits in plain files after setup (D12, D47). Keycloak with TOTP and a
client certificate make the web UI's sign-in strong (D48). Privileges are listed per container so each one can be
justified (D49). The relaxations are the settings that already exist (D50). Internal traffic is encrypted because
the services trust each other only through fabric's CA (D51).

## 5.5.1.6 Integrations, dependencies and data (D52–D55)

The owner dropped the Cockpit bridge once a community plugin showed fabric's stacks (D52). Hosts refuse extra apt
sources after a release upgrade disabled Docker's own repository on the test Pi, so the host uses only the
archive; inside images the LTS rule (D22) can need an upstream repository (D53). The owner accepted that the
images run GPL programs unchanged (D54). The data stores are the services fabric runs (D55).

## 5.5.1.7 Testing and documentation (D56–D59)

The test machines are what the owner has (D56). Hardware security modules are the only thing the owner does not
have, so they are emulated (D57). No exports are needed yet (D58). The test layout deviation is explained in 1.2.3
(D59).
