## 5.8.2.1 What the owner asked

2026-10-07, after setting up the web UI's client certificate on the test Pi: the certificate should belong to people
**on the domain**, as part of their user profile, and give them single sign-on **without a password or MFA**. The
client certificate and the authenticator stay available for those who want both ("for paranoid people").

Today (D48) every web UI sign-in needs a client certificate from fabric's CA *and* Keycloak's password and TOTP;
apps connected with `fabricctl sso` ask for the password and TOTP.

Two ways for a domain member to prove who they are without typing anything:

- **Kerberos (SPNEGO).** The domain logon already gives the person a Kerberos ticket from the site's DC. Keycloak
  accepts it with its Kerberos authenticator, beside the LDAP federation it already has. Nothing to issue, renew or
  revoke: disabling the account or leaving the domain ends it. Browsers must be told to trust `sso.<domain>` for
  Negotiate: fabric's GPO for Edge and Chrome on Windows, the Linux join script for Linux.
- **A per-user certificate** in the person's profile, which Keycloak accepts with its X.509 authenticator. Windows
  auto-enrols only from Microsoft's certificate service (MS-WCCE), which Samba does not provide, so fabric needs its
  own enrolment on Windows and Linux. Suits smart cards and TPM-bound keys.

Devices off the domain (phones, guests) keep the password and TOTP.

## 5.8.2.2 The owner's answers

2026-10-07, recorded in the register as D106–D109 (revised the same day: 5.8.2.5)
([1.2.6.3](../volume_1_systems_and_services/1.2.6-samba-decisions.md#1263-sign-in-on-the-domain-d106d111)):

- **Both methods** (D106): Kerberos by default, user certificates available too.
- **The web UI from a domain device** (D107): signed in by the domain, but asks for TOTP by default; setup asks,
  and it can be changed later.
- **The web UI's client certificate** (D108): an option, off by default, easy to turn on after the first standup —
  one of the layers an install can add as it hardens.
- **When** (D109): after 0.6.0, tested on the owner's Proxmox lab (two Windows and two Ubuntu Server VMs).

## 5.8.2.3 Impact assessment

- **Architecture.** Keycloak gains a Kerberos keytab (a service principal `HTTP/sso.<domain>` in the site's DC) and
  browser flows that try Kerberos, then a user certificate, then password and TOTP. The web UI's gate moves from
  nginx (`ssl_verify_client on`) to a setting: with the certificate on, nginx requires it as now; with it off,
  nginx asks for none and the web UI relies on Keycloak, still binding the session to what signed in. User
  certificate enrolment is a new part of the agent and the join scripts.
- **Breaking changes.** None for 0.6.0 installs that keep the certificate: D108's default (off) applies to new
  installs, and an upgrade keeps an install's current gate until the owner changes it. D48 is replaced for the web
  UI part only; Keycloak with TOTP stays.
- **Security.** Off the certificate, the admin console is reachable by any LAN device's browser up to the Keycloak
  sign-in, so password guessing and web bugs are no longer stopped at nginx. TOTP for the console (D107's default)
  and Keycloak's brute-force lockout remain. Status output and the web UI show the active layers (global Rule 10).
- **Scope creep.** User certificate enrolment for Windows is the large part; Kerberos alone covers the owner's
  domain machines. Building Kerberos first and enrolment second keeps each step testable.

## 5.8.2.5 Revised: a password by default, raised from the console

2026-10-07, the same day, after the owner asked whether a certificate could be unlocked with a Windows Hello PIN
so sign-in is not instant. The answer given: a **passkey** (WebAuthn) does that — Keycloak supports it natively,
the key is made in the PC's TPM and used only after the Hello PIN, fingerprint or face, it cannot be copied off
the device or used on a look-alike site, and phones and security keys work the same way. A certificate the user
imports is not reliably bound to Windows Hello outside Microsoft's own enrolment, which Samba lacks. Logging on
to Windows itself with Windows Hello for Business against Samba is not assumed; it is checked when this is
designed.

The owner then set the model:

- **D110:** a new install asks everyone, admins included, for a username and password; Kerberos from the domain
  logon is on by default. This relaxes global Rule 10 (secure by default); the deviation is recorded in 1.2.3.2.
  D107's TOTP default is revised away.
- **D111:** every stronger layer is raised from the web console; lowering one is possible only at the command line
  on the fabric host, as root, with the layer's name typed to confirm, an audit entry and a warning that stays in
  doctor and the web UI. No floor: the command line can lower anything. Passkeys join the layers D106 offers.

Impact beyond 5.8.2.3: until this is built, 0.6.0 keeps D48 (client certificate, password and TOTP for the web
UI). When built, an install upgraded from 0.6.0 keeps the layers it has; only new installs start at a password.
