## 5.8.2.1 What the owner asked

2026-10-07, after setting up the web UI's client certificate on the test Pi: the certificate should belong to people
**on the domain**, as part of their user profile, and give them single sign-on **without a password or MFA**. The
client certificate and the authenticator stay available for those who want both ("for paranoid people").

Today (D48) every web UI sign-in needs a client certificate from fabric's CA *and* Keycloak's password and TOTP;
apps connected with `fabricctl sso` ask for the password and TOTP.

Two ways for a domain member to prove who they are without typing anything:

- **Kerberos (SPNEGO).** The domain logon already gives the person a Kerberos ticket from the site's DC. Keycloak
  accepts it with its Kerberos authenticator, beside the LDAP federation it already has. Nothing to issue, renew or
  revoke: disabling the account or leaving the domain ends it. Browsers must be told to trust `sso.<domain>` for
  Negotiate: fabric's GPO for Edge and Chrome on Windows, the Linux join script for Linux.
- **A per-user certificate** in the person's profile, which Keycloak accepts with its X.509 authenticator. Windows
  auto-enrols only from Microsoft's certificate service (MS-WCCE), which Samba does not provide, so fabric needs its
  own enrolment on Windows and Linux. Suits smart cards and TPM-bound keys.

Devices off the domain (phones, guests) keep the password and TOTP.

## 5.8.2.2 The owner's answers

2026-10-07, recorded in the register as D106–D109 (revised the same day: 5.8.2.5)
([1.2.6.3](../volume_1_systems_and_services/1.2.6-samba-decisions.md#1263-sign-in-on-the-domain-d106d111-d114d117)):

- **Both methods** (D106): Kerberos by default, user certificates available too.
- **The web UI from a domain device** (D107): signed in by the domain, but asks for TOTP by default; setup asks,
  and it can be changed later.
- **The web UI's client certificate** (D108): an option, off by default, easy to turn on after the first standup —
  one of the layers an install can add as it hardens.
- **When** (D109): after 0.6.0, tested on the owner's Proxmox lab (two Windows and two Ubuntu Server VMs).

## 5.8.2.3 Impact assessment

- **Architecture.** Keycloak gains a Kerberos keytab (a service principal `HTTP/sso.<domain>` in the site's DC) and
  browser flows that try Kerberos, then a user certificate, then password and TOTP. The web UI's gate moves from
  nginx (`ssl_verify_client on`) to a setting: with the certificate on, nginx requires it as now; with it off,
  nginx asks for none and the web UI relies on Keycloak, still binding the session to what signed in. User
  certificate enrolment is a new part of the agent and the join scripts.
- **Breaking changes.** None for 0.6.0 installs that keep the certificate: D108's default (off) applies to new
  installs, and an upgrade keeps an install's current gate until the owner changes it. D48 is replaced for the web
  UI part only; Keycloak with TOTP stays.
- **Security.** Off the certificate, the admin console is reachable by any LAN device's browser up to the Keycloak
  sign-in, so password guessing and web bugs are no longer stopped at nginx. TOTP for the console (D107's default)
  and Keycloak's brute-force lockout remain. Status output and the web UI show the active layers (global Rule 10).
- **Scope creep.** User certificate enrolment for Windows is the large part; Kerberos alone covers the owner's
  domain machines. Building Kerberos first and enrolment second keeps each step testable.

## 5.8.2.5 Revised: a password by default, raised from the console

2026-10-07, the same day, after the owner asked whether a certificate could be unlocked with a Windows Hello PIN
so sign-in is not instant. The answer given: a **passkey** (WebAuthn) does that — Keycloak supports it natively,
the key is made in the PC's TPM and used only after the Hello PIN, fingerprint or face, it cannot be copied off
the device or used on a look-alike site, and phones and security keys work the same way. A certificate the user
imports is not reliably bound to Windows Hello outside Microsoft's own enrolment, which Samba lacks. Logging on
to Windows itself with Windows Hello for Business against Samba is not assumed; it is checked when this is
designed.

The owner then set the model:

- **D110:** a new install asks everyone, admins included, for a username and password; Kerberos from the domain
  logon is on by default. This relaxes global Rule 10 (secure by default); the deviation is recorded in 1.2.3.2.
  D107's TOTP default is revised away.
- **D111:** every stronger layer is raised from the web console; lowering one is possible only at the command line
  on the fabric host, as root, with the layer's name typed to confirm, an audit entry and a warning that stays in
  doctor and the web UI. No floor: the command line can lower anything. Passkeys join the layers D106 offers.

Impact beyond 5.8.2.3: until this is built, 0.6.0 keeps D48 (client certificate, password and TOTP for the web
UI). When built, an install upgraded from 0.6.0 keeps the layers it has; only new installs start at a password.

## 5.8.2.6 The 0.6.1 design

Proposed 2026-10-07 for the owner's approval, from D106–D111 and D114–D117. When approved, each part moves into
its home chapter (1.5.2 the web UI's gates, 1.6.2 Keycloak, 2.11.2 the GPOs, 2.10.2 the Linux join, 2.1 the
settings, Volume 3 the procedures) in the commit that builds it.

### 5.8.2.6.1 The layers and their settings

| Setting (fabric.yaml) | Values | New install | What it does |
|---|---|---|---|
| `signin_kerberos` | true / false | true (D110) | Keycloak accepts the domain logon's Kerberos ticket (SPNEGO) before asking for a password |
| `signin_admin_second_factor` | none / totp / passkey / any | none (D110) | A second factor for the **admin tools**: the web console, OpenBao's UI, AdGuard's page (D114) |
| `signin_everyone_second_factor` | none / totp / passkey / any | none (D110) | A second factor for **every sign-in**: the admin tools and every app added with `fabricctl sso` (D114) |
| `webui_client_cert` | true / false | false (D108) | nginx requires a client certificate from fabric's CA for the web console |

The levels are ordered, weakest first: none < any < totp < passkey (revised while building, 5.8.2.8: `any`
accepts either factor, so it is weaker than requiring one; a passkey cannot be phished). `any` means a person with a
passkey uses it and anyone else uses TOTP, enrolling it at their next sign-in if they have none; they may add a
passkey in Keycloak's account page. The admin tools always get at least the everyone setting: their effective level
is the higher of the two. A passkey is a second factor here (after the password or Kerberos); signing in with a
passkey alone, without a password, is for a later release.

### 5.8.2.6.2 Keycloak

- **Two flows** replace `fabric-webui-mfa`: `fabric-admin-signin` (bound to `fabric-webui`, `fabric-openbao` and
  AdGuard's client) and `fabric-signin`, the realm's browser flow (every other client, including the `app-*`
  clients of `fabricctl sso`, which no longer bind a flow of their own). Each is a copy of the stock browser flow:
  cookie, then Kerberos (ALTERNATIVE when `signin_kerberos`, else DISABLED), then the username and password form,
  then the second-factor sub-flow: DISABLED for none; REQUIRED with OTP REQUIRED for totp; REQUIRED with WebAuthn
  REQUIRED for passkey; REQUIRED with OTP and WebAuthn ALTERNATIVE for any. Converged on every apply, like today.
- **Kerberos:** a service account per site, `fabric-sso-<site>` in the site's `OU=service-accounts`, holds the SPNs
  `HTTP/sso.<domain>` and `HTTP/<hostname>.<domain>` (browsers may ask for the name a CNAME points to). Its keytab
  is exported by the samba container (`samba-tool domain exportkeytab`) into Keycloak's config folder (0400,
  Keycloak's user); its password is generated and kept like the other `ad_*` secrets. The LDAP provider gets
  `allowKerberosAuthentication`, the AD realm, the server principal and the keytab; a `krb5.conf` maps fabric's
  domain to the AD realm inside the container. Keycloak's own password check stays LDAP (not Kerberos).
- **WebAuthn policy** for passkeys: relying party `sso.<domain>`, user verification **required** (the Windows Hello
  PIN, fingerprint or face: the owner's point in 5.8.2.5), any authenticator attachment, resident keys preferred.

### 5.8.2.6.3 The web console

- With `webui_client_cert` false, nginx asks for no client certificate (`ssl_verify_client off`) and the web app
  skips the gates that read it (1.5.2 gates 1, 2 and 5); the session binds to the session cookie and the sign-in's
  ID token instead of the certificate fingerprint (gate 7). With it true, everything is as in 0.6.0.
- `prompt=login` stays: each console sign-in runs the admin flow again (silent with Kerberos and no second factor).
- Setup's first admin kit holds no `.p12` while the certificate is off; `fabricctl client-cert` still makes one,
  ready for when it is turned on.

### 5.8.2.6.4 Raising and lowering (D111, D116)

- **Raise:** a **Security** page in the web console (admins only, D116) shows every layer, its state and what
  raising it does; *Raise* asks for a fresh sign-in (the last 5 minutes, like OpenBao's unlock methods), then
  fabric-agent writes the setting to `fabric.yaml`, converges Keycloak (and nginx for the certificate) and writes
  the audit log. The page offers only raises. Turning on the client certificate warns that each admin needs their
  `.p12` first (`fabricctl client-cert`), and is refused while the signed-in admin's browser presented none.
- **Lower:** only `sudo fabricctl security lower <layer> [<level>]` on the fabric host. It states what is lost, asks
  for the layer's name typed back (`--yes` does not skip it), writes the setting, converges, and writes the audit
  log with the root user and the sudo user.
- **Status:** `sudo fabricctl security` lists the layers. A layer lowered below a level it once had is marked in
  `/opt/fabric/config/security-lowered.json` until raised again; `fabricctl doctor` and the web console's Overview
  show a warning for it. Setup (`--file` or a re-run) refuses to lower a layer of an existing install and points to
  the command; a fresh install takes any values.

### 5.8.2.6.5 Browsers (D117)

- **Windows:** the site's Windows baseline GPO (2.11.2.20) adds the Negotiate allowlist for `sso.<domain>`: Edge and
  Chrome (`AuthServerAllowlist`) and Firefox (`Authentication` → `SPNEGO`).
- **Linux:** the join script writes the same for Firefox (`/etc/firefox/policies/policies.json`) and for Chromium
  and Chrome (their managed policy folders), and maps fabric's domain to the AD realm in `krb5.conf`
  (`[domain_realm]`).
- Without them (a browser that is not configured, or a device off the domain), Keycloak shows the password form.

### 5.8.2.6.6 Not in 0.6.1

Per-user certificates (D115), signing in with a passkey alone, and logging on to Windows with Windows Hello for
Business.

## 5.8.2.7 How 0.6.1 is built and tested

In this order, each step with its tests before the next:

1. **Spike K1** (Rule 4's exception, `spikes/kerberos-sso/`): Keycloak 26 with a keytab from the Samba test DC
   accepts `curl --negotiate` for a domain person, through the `sso.<domain>` CNAME and directly; and a WebAuthn
   second factor driven by a software authenticator completes Keycloak's form flow. It answers whether the two
   SPNs and the `krb5.conf` mapping are enough.
2. **Keycloak flows and settings** (5.8.2.6.1–2): the Keycloak suite gains each level for both scopes, the refusals
   (no second factor when one is required, a wrong TOTP), Kerberos sign-in and its fallback to the password form.
3. **The web console without a certificate** (5.8.2.6.3): the sign-in suite runs both ways.
4. **The Security page and `fabricctl security`** (5.8.2.6.4): raise in the console, lower by the command with its
   typed confirmation, the audit entries, doctor's warning, setup refusing to lower.
5. **Browsers** (5.8.2.6.5): the GPO's Registry.pol entries read back; the Linux join on Ubuntu and Debian writes
   the policies and the mapping.
6. **The test Pi:** the host suite from apt `testing`; then the owner's checks on a real Windows machine: SSO in
   Edge after a domain logon, a passkey with Windows Hello, the Security page.

0.6.1 is the first production release (D113), so the settings above are the contract later releases upgrade from.

## 5.8.2.8 Spike K1 and step 2: what building changed

**Spike K1** (`spikes/kerberos-sso/`, 2026-10-07, against the keycloak suite's real DC and Keycloak 26.7):

- A keytab exported by `samba-tool domain exportkeytab` for a service account with two HTTP SPNs lets Keycloak accept
  a domain person's ticket with server principal `*`, both for `sso.<domain>` and for the host name a client
  canonicalises a CNAME to. The AD vendor's principal attribute (`userPrincipalName`) matches Samba's.
- **The account must be AES-only** (`msDS-SupportedEncryptionTypes` 24): without it Samba issues RC4 tickets and
  Java refuses them ("Encryption type RC4 with HMAC is not supported").
- Without a ticket Keycloak answers `401 Negotiate` with a page that continues to the password form (a browser
  submits it at once).
- A person made by fabric must change the one-time password before the KDC gives them a ticket (at their first
  Windows log-on in practice).

**Step 2** (Keycloak's flows and settings), changes to 5.8.2.6:

- Keycloak's stock browser flow puts Kerberos beside the password form at the top, so a Kerberos sign-in would skip
  the second factor. fabric builds its flows itself: the cookie (realm flow only), then a first factor (Kerberos or
  password), then the second factor. The admin flow takes no session cookie, which also closes a 0.6.0 gap (a
  sign-in through Keycloak's account page carried into OpenBao's UI without TOTP).
- With TOTP and a passkey both ALTERNATIVE, Keycloak sends someone who has neither to the passkey sign-in page, where
  they cannot go on. `any` is therefore a passkey sub-flow (only for someone with one) followed by a TOTP sub-flow
  that runs when the passkey one did not (Keycloak's "sub-flow executed" condition).
- The levels' order became none < any < totp < passkey (5.8.2.6.1).
- The keycloak suite proves it with a real DC and Keycloak (44 checks): the flows and their bindings, the default
  (a password only), raising the admin tools to TOTP (the console then asks for it; other sign-ins do not; the
  console ignores an app's session), Kerberos from a domain client (no password; still the console's TOTP; through
  the CNAME's name; the fallback; `signin_kerberos` off), passkeys with a software authenticator that reports user
  verification (registration, sign-in, a wrong key refused), and `any` (a passkey used; TOTP enrolled by someone with
  neither).

## 5.8.2.9 0.6.1 on the test Pi

2026-10-07, `rc/0.6.1` (images 0.6.1-rc.40, pinned; the package from the apt `testing` suite), a fresh install on the
test Pi (Ubuntu 26.04 arm64, 4 GB): the host suite passed whole (22, setup 10 minutes) — the default sign-in (no
certificate asked, the admin in with a password only, a non-admin refused), the password-only sign-in listed as a
relaxation, `fabricctl security raise` for TOTP and the client certificate (applied: nginx, the web app, Keycloak),
the setup re-run issuing the admin's `.p12` once the console asks for one, the strict sign-in after it (TOTP, the
certificate refusals), and a lowering through a terminal (a wrong name and `--yes` refused; the right name lowers it;
doctor warns and still passes; the audit log has it).

The first run failed two checks, both fixed: the strict sign-in test expected the password form first (a browser
without a Kerberos ticket now passes Keycloak's continue page before it), and `fabricctl security` said done while
the web console it had restarted was still starting, so doctor right after saw a 502 (it now waits for it).

The sandbox on the pinned images: 169 of 170 in each of two runs. The first missed only the two sign-in checks
above. The second passed them and failed the intermittent rollback of a bad nginx image seen in 0.6.0 (5.8.1.27): the
rollback's start failed in a control process ("the update failed and so did the rollback"); the first run passed it.
Not caused by 0.6.1 (the code involved did not change), but `fabricctl images update` matters in production, so
`start_unit` now stops a unit that is not cleanly active before starting it (ending a restart loop the bad image may
still be in), and the sandbox keeps nginx's journal from that step for the next failure. One intermittent failure
cannot prove the cause: it stays on watch. The third run, with the change, passed whole (170).
