## 1.8.4.1 Configuration

Enabled by default whenever `install_keycloak: true` (`install_webui` is forced off without Keycloak).

| Variable | Default | Notes |
|----------|---------|-------|
| `install_webui` | `true` | Effective only with Keycloak |
| `webui_hostname` | `fabric.<domain>` | The web UI's address — any host name. Inside the domain a CNAME to this host is added automatically; outside it, point DNS at the host yourself. The certificate and the OIDC redirect follow |
| `cname_mgr` | `fabric` | The default name's label (`<cname_mgr>.<domain>`) when `webui_hostname` is not set |
| `webui_realm` | `domain` | Keycloak realm |
| `webui_admin_role` | `fabric-console-admin` | The admin bundle (every permission), granted to `webui_admin_group` |
| `webui_admin_group` | `admins` | Group granted the role; its members can only be reset by an admin |
| `webui_admin_user` | `fabric-admin` | First admin, created by setup with the password chosen there (asked interactively, or `--admin-password-file`; kept once chosen; 2.1.6.33) |
| `webui_admin_email` | `<user>@<domain>` | Mail attribute of that user (Keycloak's profile needs one) |
| `webui_client_cert_days` | `365` | Lifetime of the admins' client certificates |
| `webui_client_cert` | `false` (2.1.8.2) | The web console asks for a client certificate from fabric's CA; raised in the web console, lowered only with `fabricctl security lower` (2.1.6.24) |
| `signin_kerberos` | `false` (asked at setup, 2.1.6.32) | Keycloak accepts a domain logon's Kerberos ticket (2.3.6.2.6.2) |
| `signin_admin_second_factor` | `none` | The admin tools' second factor: `none`, `any`, `totp`, `passkey` (weakest first); raised in the web console, lowered only with `fabricctl security lower` (2.1.6.24) |
| `signin_everyone_second_factor` | `none` | Every sign-in's second factor, same levels; the admin tools never get less |
| `webui_session_idle` | `900` | Seconds |
| `webui_session_max` | `28800` | Seconds |
| `webui_oidc_secret` | *(generated)* | With fabric's secrets (OpenBao) |

Related: `image_webui` (`fabric/web:local`), `ip_webui` (`10.255.0.80`), `service_users.webui` (uid/gid `912`) — see [vars.md](1.1.8-about-settings.md#1181-the-settings-file).

After changing the realm/role/group vars: `sudo fabricctl --apply` then `sudo fabricctl --keycloak-sync`.

The groups that carry the other bundles (`auditors`, `network-operators`, `equipment-operators`, `pki-operators`, `helpdesk`) come from `ldap_groups` (each entry's `bundle`); see [vars.md](1.1.8-about-settings.md#1181-the-settings-file).

Image updates: `sudo fabricctl images update fabric-web` rebuilds the image on the validated Debian base (pinned by digest). The Debian base is shared (`image_debian`), so bind9, samba, kea and freeradius move to it together. An apply that changes the app code or Dockerfile rebuilds the image; `fabric-web` is always restarted last with `--no-block`, since the apply may have been started from the web UI.

## 1.8.4.2 Doctor and image updates on the Overview

Built 2026-10-08 for 0.6.3 (decision 2.1.8.3; design 2.3.1.11.5).

- **Run doctor** (`status:read`): the same end-to-end checks as `fabricctl doctor` (`setup/verify_install.checks`, as
  data by `setup/doctor_report`), each shown with its result; OpenBao locked is one failed check, since the others need
  fabric's secrets. They run as a transient systemd unit (`systemd-run`), outside fabric-agent's sandbox: the agent
  may reach only localhost and `fabric_net`, while doctor asks DNS and nginx at the host's LAN address as a client
  would (found by the 0.6.3 sandbox).
- **Updates** (the table needs `status:read`; changing needs `images:update`, new, admins only): what `fabricctl images
  status` shows per service, with *Update* where one is available and *Roll back* (to the image before the last
  update). Each is `images/apply_image_action`: the same health-gated switch as the command, audited with the person
  who asked; a service that does not come up healthy goes back by itself. The web console sits behind the admin tools'
  second factor when that layer is raised (2.1.6.27), so these do too.
- **Jobs.** Both take seconds to minutes, longer than a request, so each runs as a fabric-agent job (`agent/job_store`,
  in memory): `POST /v1/jobs/doctor` or `/v1/jobs/images` starts it and answers its id; `GET /v1/jobs/<id>` reads it,
  only for the person who started it (another person's id is "no such job"). The job's page reloads itself every 2
  seconds while it runs: a meta refresh, so the pages keep their strict CSP (no script). An agent restart forgets its
  jobs; the changes they made stand.
- **Tests:** the `webui` suites (the forms per bundle, the agent's 403 for `images:update`, a doctor job read back by its
  owner and refused to another person); the sandbox runs doctor and an image update as agent jobs on a real install.
