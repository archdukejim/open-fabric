## 1.12.2.2 Shape

```
clients ── host_ip:53 ──> bind9-resolver (recursive, response policy zones)
                              ├─ fabric's zones ──> bind9 (authoritative, bind_dns_port 5053)   never filtered
                              └─ internet names ──> Cloudflare over DoT (1.1.1.1, 1.0.0.1)
```

A second BIND, `bind9-resolver`, answers clients; the authoritative BIND (1.4.1) stays authoritative-only, so a bad
list or a resolver restart never touches the zones ACME, Kea, federation and the AD zone depend on. DHCP hands out
only an address, so whatever answers clients is on 53 (1.12.1.2): the resolver takes `host_ip:53` and BIND moves to
`bind_dns_port` (5053), as it does behind AdGuard.

## 1.12.2.3 Settings

The settings are listed in [1.1.9.9](1.1.9-optional-parts.md#1199-dns-filter-the-bind-resolver); they live in the
vars file, so a reinstall keeps them. `dns_filter: bind` turns the resolver on (`install_resolver`).

## 1.12.2.4 The container

- **`bind9-resolver`**, from fabric's `bind9` image (the same BIND 9.20, 2.1.1.5) with a configuration of its own.
  It is a unit of its own with no `requires`: an apply that restarts the authoritative BIND never takes the clients'
  DNS down.
- **Its own service account**, `resolver` (`fabric-resolver`, 613): it reads the lists and writes its logs, and
  nothing of the authoritative BIND's (keys, zones, the AD zone's database).
- On `fabric_net` at `ip_resolver` (10.255.0.33). No capabilities, read-only root, `no-new-privileges`; Docker
  publishes `host_ip:53` (TCP and UDP) to its port 53.
- `named -f` (not the image's `-g`, which ignores the logging statement, 2.3.12.1.16).
- Memory limit `resolver_mem_limit`, **384 MiB** (2.1.12.3): the default list takes about 192 MiB (2.3.12.1.17).
- Health check: `rndc status` with the resolver's own control key (`resolver_rndc_secret`, generated per install).
- Certificates for the upstream's DoT: the host's CA bundle (`/etc/ssl/certs/ca-certificates.crt`), mounted
  read-only, kept current by the host's updates.
- Folders under `<base>/resolver/`: `config` (named.conf and the rules zones, rendered at apply), `lists` (the
  converted lists, written by the list job), `log` (the query and RPZ logs), `cache` (named's working folder).

## 1.12.2.5 The main view

One view in step 2, `everyone` (groups are chained views on it from step 6, 2.3.12.1.16):

- `recursion yes` for the networks AdGuard allowed (`lan_cidr`, `fabric_subnet`, `security.firewall_allow`);
  everyone else is REFUSED.
- **fabric's zones** — this site's domain, the organisation's, the linked sites', the reverse zones, the AD zone —
  are forward zones to the authoritative BIND (`ip_bind9`, port 53 on `fabric_net`), and `validate-except` (a
  private zone has no DNSSEC chain from the root).
- `dnssec-validation auto` for everything else.
- `response-policy`, first match wins: **`fabric.rpz`** (passthru for fabric's zones: never filtered, even when a list
  names them) → **`owner.rpz`** (the owner's allows and blocks) → **one zone per list**, in the settings' order.
  `break-dnssec yes` and `qname-wait-recurse no`.
- A blocked name answers **NXDOMAIN** (2.1.12.3).

## 1.12.2.6 Lists: fetched, converted, loaded

- A list is `{name, url}` in `dns_filter_lists`; the default is the **AdGuard DNS filter** (2.1.12.3).
- **Converting** (`dns_filter/convert_list`): hosts files, plain domains, RPZ as published, and AdGuard's DNS syntax
  (`||name^`, `@@||name^`, `||*.name^`, `$denyallow`, `$dnsrewrite` to a name, `$badfilter`, `$important`,
  `||1.2.3.4^` as an `rpz-ip` trigger). Rules RPZ cannot express are **skipped and counted**, never guessed:
  wildcards inside a name, regular expressions, other modifiers, unanchored patterns. What the spike measured:
  2.3.12.1.16.
- **Each list is a zone of its own**, `<id>.list.rpz`, where `<id>` is the first 12 hex digits of the SHA-256 of
  its URL, so reordering or renaming a list does not reload it. The RPZ log names that zone, so a block is traced
  back to its list.
- **Checks before a list is used:** at least one rule converted, at most 2,000,000 RPZ records, `named-checkzone`
  passes. A list that fails keeps its last good copy; a list never fetched yet is left out of the configuration,
  so the resolver never starts on a missing file.
- Each list's state is kept in `<base>/resolver/lists/state.json`: last fetch, last success, rules converted and
  skipped, RPZ records, its estimated memory (records × 0.53 KB, 2.3.12.1.17) and the last error.

## 1.12.2.7 The owner's rules

`dns_filter_allow` and `dns_filter_block`: names, each meaning **the name and every name below it** (AdGuard's
`@@||name^` and `||name^`). They make `owner.rpz`, before every list: an allow beats every list, a block applies
whatever the lists say. A name in both, or one inside fabric's own zones, is refused by the settings check.

## 1.12.2.8 Upstreams

`dns_filter_upstreams`: `[{address, name}]`, forwarded to over **DoT** (port 853) with the certificate's name
verified. Default: Cloudflare, `1.1.1.1` and `1.0.0.1`, name `cloudflare-dns.com` (2.1.12.3). `[]`: no forwarders —
BIND resolves from the root servers itself (plain DNS to the internet's servers).

## 1.12.2.9 Logs

- **Query log** and **RPZ log**, each a file in `<base>/resolver/log` (rotated: 2 × 20 MB). The query line names the
  client and its view (the group, from step 6); the RPZ line names the rule's zone (the list or `owner.rpz`).
  Read into Postgres by the query-log job (1.12.2.13).
- Everything else (start, loads, errors) to the journal, like every container.

## 1.12.2.10 Deploy, apply and the list timer

- **Apply** renders the configuration and the rules zones; a change is reloaded by the running resolver (`rndc
  reload`: the configuration and every zone whose file changed), or the resolver restarts when its compose file
  changed. A list in the settings that has no converted copy yet is fetched
  during the apply (the resolver then starts with it); an apply offline leaves it out until a fetch succeeds.
- **`fabricctl dns-filter lists`** fetches every list now, converts it, and reloads only the zones that changed
  (`rndc reload <zone>`): the others keep answering. `--scheduled` is the timer's run.
- **`fabric-dns-lists.timer`**: daily at 04:15 (spread by up to 30 minutes, a missed night runs at boot), only while
  `dns_filter` is `bind`.
- **`fabricctl dns-filter status`**: each list's state (1.12.2.6) and the resolver's.

## 1.12.2.12 Moving from AdGuard Home (0.6 → 0.7)

`fabricctl setup` after the upgrade does it (2.3.12.1.9); `fabricctl --apply` alone refuses `dns_filter: adguard`
and says to run setup.

- **Settings** (`setup/move_dns_filter`, while the settings are collected): AdGuard's own configuration when it ran,
  else the `adguard_*` settings, becomes the resolver's (`dns_filter/import_adguard_settings`): upstreams as DoT by
  address where the provider's certificate name is known (Cloudflare, Google, Quad9, AdGuard DNS), the enabled lists
  by URL, `||name^` and `@@||name^` rules as `dns_filter_block` and `dns_filter_allow`. Settings the admin already set
  are kept. The `adguard_*` keys go, and `dns_filter` becomes `bind`.
- **What does not move** is listed by setup and kept in `<config>/dns-filter-import-<time>.json` with AdGuard's
  configuration (its local user's password hash left out): upstreams with no known certificate name, plain-DNS
  upstreams, switched-off lists, allowlists, rules other than `||name^`/`@@||name^`, safe search and AdGuard's
  clients (back with client groups, step 6), parental control, safe browsing, blocked services, DNS rewrites.
- **AdGuard leaves the host** (`setup/retire_adguard`, at the start of the start step, so the resolver can take port
  53): its units and containers, `<base>/adguard` and `<base>/adguard-auth` (once the record exists), nginx's
  sign-in snippet, the local image, its three secrets and its two accounts (`fabric-dnsfilter`, `fabric-auth`);
  Keycloak's `fabric-adguard` client is removed by the Keycloak step. Idempotent: a later run finishes what is left.

## 1.12.2.13 The query log and statistics

Decisions 2.1.12.4 (7 days, admins only; statistics without client addresses, 90 days) and 2.1.12.5 (collected
every 5 minutes and on demand).

- **Where:** fabric's Postgres, a database `dnslog` owned by a role of its own, `fabric_dnslog`; no other role may
  connect to it (`CONNECT` revoked from `PUBLIC`), so Keycloak's role never sees it. It exists only where Postgres
  does (`install_keycloak`, on by default): without it the resolver still logs to its files, and the status says
  the query log is off.
- **How fabric talks to it:** SQL on stdin to `psql` in the Postgres container over its local socket, as fabric's
  other Postgres work does (`setup/ensure_db_rotation`): no client library on the host, no password, nothing on a
  command line but checked values. Searches are bound as `psql` variables (`:'name'`), never pasted into SQL.
- **Tables:**

  | Table | Holds | Kept |
  |---|---|---|
  | `queries` | time, client address and port, view (the group), name, type; when a response policy rewrote it: the action (`NXDOMAIN`, `PASSTHRU`, `Local-Data`) and the zone (a list's `<id>.list.rpz`, `owner.rpz`, `fabric.rpz`), `blocked` when the answer was NXDOMAIN | 7 days |
  | `stats_hourly` | per hour and per zone (`''` for all): queries, blocked | 90 days |
  | `stats_blocked` | per day: blocked names, their zone and count (no client) | 90 days |

- **Collecting** (`dns_filter/ingest_dns_log`): the new lines of `query.log`, then of `rpz.log`, from where the last
  run stopped; a rotated file (BIND renames it `.0` at 20 MB) is finished first, found by its inode. Each RPZ line
  marks its query (same client, port and name, within 2 seconds). The hours and days the run touched are recomputed
  from `queries`, so the statistics never drift. Then rows past 7 days (queries) and 90 days (statistics) go. Its
  place in the files is kept in `<base>/resolver/ingest.json` (root's: the resolver cannot move it) and moves only after Postgres took the lines.
- **When:** `fabric-dns-log.timer` every 5 minutes (`fabricctl dns-filter ingest --scheduled`, installed while the
  resolver and Postgres are both on), and before every read below, so what is shown is current.
- **Reading:**
  - `fabricctl dns-filter log [--client ADDRESS] [--name NAME] [--blocked] [--limit N]`: newest first, at most 500;
    a name matches it and every name below it.
  - `fabricctl dns-filter stats`: the last 24 hours by hour, the last 7 days' totals, blocked per list, the top
    blocked names.
  - Agent: `GET /v1/dns-filter` (statistics and each list's state, `dns:filter`) and `POST /v1/dns-filter/querylog`
    (a search in the body, `dns:querylog`: the admin bundle only). The web console's tab uses them (step 5).
