## 3.15.1.1 What works so far

The Windows domain is being built in steps (design: [2.11.2](../volume_2_technologies_and_features/2.11.2-samba-dc.md),
[1.6.3](../volume_1_systems_and_services/1.6.3-samba-directory.md)). Today (build step S1, beside 389-DS):

- a Samba AD domain controller on the host's address, hardened (1.3.9);
- the domain kept as fabric wants it after every setup and apply (3.15.1.4);
- the password policy, chosen by you.

Not yet:

- people and devices in AD (S2), sign-in through it (S3);
- 802.1X PEAP (S4);
- joining Windows (S5) and Linux machines (S6).

While the domain is on, nginx no longer serves 389-DS on ports 389/636 (the domain controller owns them). Linux
clients set up against `ldap.<domain>` lose 389-DS until S6.

## 3.15.1.2 Turning it on

In setup's **Advanced** plan, answer yes to *a Windows domain*. Setup then asks:

- **The AD domain.** It is permanent: it cannot be changed once the domain exists. `ad.<domain>` is recommended,
  and it is needed to federate sites or locations later. fabric's own domain is not supported yet.
- **Every value of the password policy.** Nothing is preselected (D89).

Or set them in the settings file, then run `sudo fabricctl setup` (an unattended setup refuses without them):

```yaml
install_samba: true
ad_domain: ad.example.org
ad_password_policy: {minimum_length: 14, complexity: true, history: 24, minimum_age_days: 1,
                     maximum_age_days: 0, lockout_threshold: 5, lockout_minutes: 15, lockout_window_minutes: 15}
```

Setup asks before opening the domain controller's ports in the host firewall (the `firewall` host change, 2.7.1).
The ports are opened to the LAN, `security.firewall_allow` and fabric's container network. Every setting:
[2.1.9.7](../volume_2_technologies_and_features/2.1.9-optional-parts.md#2197-windows-domain-optional-samba-ad).

## 3.15.1.3 Status and the password policy

```bash
sudo fabricctl domain status
```

Shows:

- the domain and this domain controller, and whether it runs;
- the domain-wide roles it holds;
- the password policy in force.

```bash
sudo fabricctl domain password-policy --minimum-length 16 --lockout-threshold 10
```

This changes those values and applies them. The whole policy is checked again; for example, a lockout shorter than
its reset window is refused, as AD requires. Without options it shows the policy in the settings. `--no-apply`
records the change for the next `sudo fabricctl --apply`.

## 3.15.1.4 What fabric keeps in the domain

fabric re-checks these after every setup and apply. It changes only what differs and leaves your own objects alone.

- **Schema:** fabric's and sudo's attributes in AD's schema. They are added once and never removed: AD's schema is
  permanent.
- **Layout:** `OU=sites`, with one OU per site (people, groups, machines, devices, device roles, networks, sudo rules,
  service accounts). The root site's OU also holds `OU=organisation`. New users and computers made with Windows'
  own tools land in the root site's OU.
- **Groups:** `<site>-users`, `<site>-admins`, `fabric-admins` and `fabric-break-glass`.
- **Site admins:** `<site>-admins` may change their own site's OU and nothing else, and not its service accounts.
- **AD site:** the AD site of this fabric site, with this site's networks as its subnets.
- **Password policy:** the policy you chose.
- **Group Policy:** two GPOs. *fabric: trust in fabric's root CA* (linked to the domain) and
  *fabric: `<site>` log-on rights*. The second lets the site's people and admins, `fabric-admins` and
  `fabric-break-glass` log on to the site's machines.
