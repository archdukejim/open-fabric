## 2.1.12.1 Is the DNS filter part of an install, and what does it start with

- **Decision:** **On by default** (`dns_filter: adguard`; `none` turns it off), shown on setup's plan and asked in Advanced. A first deploy sends internet lookups to **Cloudflare** over DNS-over-HTTPS (by address) and turns on the **AdGuard DNS filter** list ([1.12.1.3](../volume_1_description_and_architecture/1.12.1-adguard.md#11213-settings)).
- **Shapes:** 1.12, 3.3
- **Made:** 2026-10-07, by the owner, in 0.6.0. Replaces the 2026-10-01 choice of local DNS only.
- **Why:** the owner expected the filter in the stack; [2.3.6.1.27](2.3.6-identity-notes.md#236127-before-060-uninstall-reinstall).
- **Status:** In force; **revised by 2.1.12.3 on 2026-10-08**: the filter is BIND's resolver, not AdGuard; internet names go to Cloudflare over DoT, not DoH; lists are converted to RPZ from AdGuard's catalogue, with the AdGuard DNS filter still the default. Still on by default.

## 2.1.12.2 DNS-over-TLS on 853, answered by AdGuard

- **Decision:** AdGuard answers DoT with the DNS name's certificate (or the public wildcard), so encrypted queries are filtered too; 853 joins the ports only with the filter on; doctor checks DoH's `/dns-query`.
- **Shapes:** 1.12, 1.4
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** 2.3.1.11.6.
- **Status:** In force; the DoH check **built 2026-10-08** (doctor, `verify_install`: a DNS query over `https://<dns name>/dns-query` must answer the host's address). **Revised by 2.1.12.3 on 2026-10-08**: the BIND resolver answers DoT, not AdGuard, in 0.7 (not 0.6.3); built after the spike ([2.3.12.1](2.3.12-dns-filter-notes.md#23121-proposal-07--bind-filters-dns-managed-in-fabrics-web-console-and-adguard-home-goes)).

## 2.1.12.3 Which engine filters DNS, and where it is managed

- **Decision:** A second BIND (`bind9-resolver`) answers clients and filters with response policy zones; lists, rules, per-client groups, the query log and statistics are managed in fabric's web console; AdGuard Home is removed, its settings imported on upgrade (anything that cannot move is reported). Internet names go to Cloudflare over DoT by address; the lists are **AdGuard's catalogue** (its HostlistsRegistry, read live), any added on demand and converted to RPZ (rules RPZ cannot express are skipped and counted), with the **AdGuard DNS filter** on by default; client groups are addresses and subnets (devices, roles and DHCP scopes with Kea in 0.8), each a view chained to the main one, so the lists are loaded once and a group only adds — safe search, its own lists and rules, names it allows — and never switches a shared list off (owner 2026-10-09, after the spike); the resolver's memory limit is 384 MiB, each list's cost shown before it is added; a blocked name answers NXDOMAIN (no block page: it cannot work for HTTPS); statistics are kept 90 days; safe search per group, off by default, comes in the same release; no services are blocked as such and there are no schedules (2.3.12.1.14). A spike on the test Pi comes first ([2.3.12.1](2.3.12-dns-filter-notes.md#23121-proposal-07--bind-filters-dns-managed-in-fabrics-web-console-and-adguard-home-goes)).
- **Shapes:** 1.12, 1.4, 1.8, 3.3, 4.12
- **Made:** 2026-10-08, by the owner ("bind9 replaces adguard with our ui handling"), first for 0.6.3, then **0.7, a release of its own** (the owner, the same day: "a new feature and a major milestone"; the later releases moved up one, 1.1.4.6); the questions of 2.3.12.1.11 answered the same day.
- **Why:** one DNS engine and one UI; per-client policy from fabric's own device and network data; 2.3.12.1.10.
- **Status:** In force; the spike first, and its findings may revise the list, the upstream and the memory limit. Revises 2.1.12.1 and 2.1.12.2.

## 2.1.12.4 How long the DNS query log is kept, and who reads it

- **Decision:** Query-log entries are kept **7 days** and read by **admins only** (a permission of their own); statistics are kept as counts without client addresses.
- **Shapes:** 1.12, 1.8
- **Made:** 2026-10-08, by the owner, for the filter proposed in 2.1.12.3.
- **Why:** enough to trace a block reported days later; the log names who looked up what, so it is personal data and kept short and narrow.
- **Status:** In force (applies to the filter that 2.1.12.3 settles).
