## 2.3.5.3 Proposal: 0.6.3 — certificate renewal, the info page, upgrade and image-update tests

### 2.3.5.3.1 What the owner asked

On 2026-10-08, for a 0.6.3 of small items before the 0.7/0.8 work that needs isolated networks or hardware:

- **Upgrade in place, tested**, as 2.1.1.32 requires from 0.6.1 on (0.6.2 shipped without it).
- **Image updates, tested:** each container one small version back, then updated.
- **Certificate renewal.** Service certificates live **90 days** and are renewed with **30 days left** (overlap well
  inside the browsers' shrinking limits: 200 days from March 2026, 100 from 2027, 47 by 2029). Certificates fabric
  cannot renew itself are **warned about ahead**. Upgrading to 0.6.3 **re-issues** today's long-lived service
  certificates. The **CA's lifetime is asked at install** (in Advanced; the root's, default **10 years**; the
  intermediate follows it).
- **The instructions page** (today the landing page at `<domain>`) moves to **`info.<domain>`**, always reachable
  over **plain HTTP** as well as HTTPS, with the CA download and the root's fingerprint; `<domain>` and the host's own
  name redirect to it.

### 2.3.5.3.2 How it works today

- **Service certificates** (the table in `setup/mint_service_certs.py`: nginx's hosts, BIND, OpenBao, Keycloak and
  Postgres, the DC, FreeRADIUS) are minted from Step-CA by `pki/mint_cert.py` with `cert_service_days`: 365 in
  `vars.yaml.j2`, a 5475-day fallback in code. They are renewed only when `fabricctl setup` or `fabricctl certs` runs;
  `pki/needs_renewal.py` already renews one with under 30 days left, missing, not from the CA, or without a SAN. A
  renewal **restarts** each affected service. **Nothing runs on a schedule** (1.5.1.2 says so).
- **The CA:** `setup/init_pki.py` makes the root with a hard-coded 10 years (`--not-after 87600h`) and lets `step ca
  init` choose the intermediate's lifetime. `cert_root_ca_days` (1825) and `cert_intermediate_days` (1095) exist in
  the settings, but the root does not read them; `cert_intermediate_days` is used only for federation site CAs.
- **Certificates fabric cannot renew:** device and people certificates (the PKI page already marks those with under
  30 days "expires soon"), the web UI's admin client certificate (365 days, renewed only by setup), and the CA's root
  and intermediate. `fabricctl status`, `fabricctl doctor` and the web UI's overview show no expiry today.
- **The landing page** is HTTPS only, at `hostname_landing` (`<domain>` unless `landing_page_cname` is set) and the
  host's own name; plain HTTP redirects everything to HTTPS except `/certs/` and the certs host, which answers on both.
- **Upgrades:** the `.deb`'s postinst only asks for `sudo fabricctl setup`; `setup/upgrade_vars.py` migrates settings.
  The sandbox upgrades a package built from the same source onto itself; nothing upgrades from an actual previous
  release.
- **Image updates:** `fabricctl images status/update/rollback` work (health-gated, restoring on failure); the sandbox
  tests update and rollback for nginx only.

### 2.3.5.3.3 Service certificates: 90 days, renewed at 30 left

- `cert_service_days` defaults to **90**, in the settings and in code (one default). Step-CA's maximum
  (`stepca_cert_max_lifetime_hours`) follows it, as now.
- **A daily timer**, `fabric-certs.timer` (fabric's own unit, under `fabric.target`, in the `services` consent group
  like the others), runs `fabricctl certs --scheduled` at a quiet hour with a random delay. It renews only what
  `needs_renewal` says (30 days left, so from day 60 a failed night is retried every night for a month).
- **Picked up without downtime where the service allows it:** nginx and Postgres **reload**; OpenBao gets **SIGHUP**
  (it re-reads its listener certificate; a restart would leave it sealed on a host unlocked only by a USB stick or a
  security key); Keycloak re-reads its certificate by itself (`https-certificates-reload-period`); BIND, the DC and
  FreeRADIUS **restart** (seconds). Which applies is a table beside the certificates table, tested per service.
- **Failure is loud:** each run records its result (`/var/lib/fabric/certs/last-renewal.json`). A failed run, or any
  service certificate under **14 days**, is a warning in `fabricctl status`, a failure in `fabricctl doctor` and a
  banner on the web UI's overview. The timer's journal holds the detail.
- **A certificate longer-lived than the setting is re-issued** (a new `needs_renewal` reason): this is how the
  upgrade to 0.6.3 replaces today's 365-day and 5475-day certificates, and how a lowered setting takes effect.
- `fabricctl certs` without `--scheduled` stays as it is (renews what needs it; `--force` renews everything), now
  with the same reload table.

### 2.3.5.3.4 Certificates fabric cannot renew: warned ahead

- **The root and intermediate CA:** warned **180 days** before either expires (status, doctor, the web UI's
  overview); replacing them stays a manual procedure (3.5).
- **The web UI's admin client certificate** (when that layer is on): warned 30 days ahead; renewed by `fabricctl
  setup`, as now.
- **Device and people certificates:** the PKI page keeps its "expires soon" mark (30 days); the overview gains a
  count of those expiring soon and expired, linking to the page.

### 2.3.5.3.5 The CA's lifetime, asked at install

- **One question, the root's lifetime** (`cert_root_ca_days`, default **3650**, i.e. 10 years), shown on setup's plan
  with its default and changed in **Advanced**; at least 365 days. `init_pki` uses it instead of the hard-coded
  10 years.
- **The intermediate follows:** its lifetime is the root's **less one year** (9 years by default), passed to `step ca
  init`, so it never outlives the root and leaves a year to replace it before the root ends. `cert_intermediate_days`
  keeps its one use, federation site CAs (capped at the root, as now).
- **Fixed once the CA exists:** on an existing install the question is not asked, and a changed value is refused
  with the reason (a CA's lifetime cannot change once it is made). Existing installs keep their CA.

### 2.3.5.3.6 The info page at info.\<domain\>, over HTTP too

- `landing_page_cname` defaults to **`info`**, so `hostname_landing` is `info.<domain>` (a value already set is
  kept). BIND gets the record like any other name.
- **`info.<domain>` answers on HTTP and HTTPS, with no forced redirect:** the instructions, the CA files and the
  **root's SHA-256 fingerprint**, so a person on a new device can fetch the CA over plain HTTP and check it before
  trusting it. Everything else stays HTTPS-only: the manual (`/manual/`) and the "This network" links stay on HTTPS,
  and the plain-HTTP page links to them there.
- **`<domain>` and `<hostname>.<domain>` redirect** (301) to `info.<domain>`: HTTP to its HTTP page, HTTPS to its
  HTTPS page, so old bookmarks keep working. The page's service certificate covers all three names.
- The certs host (`certs.<domain>`) stays as it is.

### 2.3.5.3.7 Upgrade-in-place test, every release

A host test, `tests/host/upgrade.sh`, run on the test Pi before each release from 0.6.3 on:

1. remove fabric (purge), install the **previous release** from apt `stable` and set it up non-interactively;
2. **seed state:** a person with a password, a DNS record marked for the info page, an issued device certificate, an
   AdGuard filter setting, an application secret in OpenBao, a raised sign-in layer;
3. **upgrade** to the candidate from apt `testing` and run `fabricctl setup`, as an operator would;
4. **check it survived:** the person signs in with the same password; the CA's root is the same file; the record, the
   certificate (still valid against the CA), the AdGuard setting, the secret and the layer are all still there; then
   the whole host suite.

First run: **0.6.1 → 0.6.2**, to catch up on the release that skipped it; then 0.6.2 → 0.6.3 for this release. The
results go in the release's notes, and the procedure goes in 3.1 as a step of every release.

### 2.3.5.3.8 Image-update test, one version back for every image

- A test, `tests/images/update.sh`, run in the sandbox (amd64) and once on the test Pi (arm64), for **every image**
  in the lock: the upstream ones (nginx, Step-CA's base, Keycloak, Postgres, OpenBao, Fluent Bit, AdGuard,
  oauth2-proxy, cosign) and fabric's own published ones (adguard, bind9, freeradius, kea, keycloak, samba, stepca,
  webui).
- For each: pin the **previous version**, by digest (the previous patch release on the image's tracked line for an
  upstream image, the previous published build for fabric's own), and deploy. Then check that `fabricctl images
  status` shows the update, `fabricctl images update` applies it, the service is healthy and the running digest is
  the lock's; then that **rollback** returns the previous one; then update again.
- The previous versions are listed in a test fixture (`tests/images/previous.yaml`), each pinned by digest and
  refreshed when the lock moves. An image whose track has no earlier patch is listed as skipped, with the reason.

### 2.3.5.3.11 Impact assessment

- **Architecture:** a scheduled job for the first time (one systemd timer, fabric's own); a reload table beside the
  certificates table; one new setting asked (`cert_root_ca_days`, now used); `landing_page_cname` gets a default.
  No new container, port or dependency.
- **Breaking changes:**
  - **Short certificates make renewal load-bearing:** if the timer stops, services fail within 90 days. Mitigated by
    a month of nightly retries, warnings from 14 days left, a failure in `fabricctl doctor`, and the upgrade and
    sandbox tests renewing for real.
  - **The info page moves:** `<domain>` now redirects; anything that used the page there still reaches it.
  - **Upgrading re-issues every service certificate once** and reloads or restarts their services: a few seconds per
    service during `fabricctl setup`, as any certificate change today.
  - Changed defaults: `cert_service_days` 365 → 90; the root's lifetime from a fixed 10 years to the setting (the
    same default); `cert_root_ca_days` 1825 → 3650 (unused until now, so nothing changes for existing installs).
  - Design chapters changed: 1.5.1 (renewal, lifetimes), 1.5.2 (the settings), 1.4.2 (the info page), 1.2.9 (the
    timer under `services`), 1.14.2 (the update test), 3.1 (the release procedure), 3.3.2 and 4.4.4 (where the
    instructions are).
- **Scope creep risk:** low to moderate. The pieces are separate and each is small; the risk is in the tests (an
  upgrade run on the Pi takes about an hour, and finding a previous digest for seventeen images is fiddly). Not in
  scope: ACME for services, email alerts, automatic CA replacement, per-user certificates.

### 2.3.5.3.12 Order of work and how it is tested

1. The upgrade test, run first as **0.6.1 → 0.6.2** (the catch-up), so a broken upgrade path is known before
   anything else changes.
2. Certificate lifetimes, renewal, the timer and the reload table; the warnings; the CA question. Positive and
   negative tests for each entry point (global Rule 9): `fabricctl certs --scheduled`, the Advanced question (a value
   too short; a change on an existing CA, refused), the status, doctor and web UI warnings, and a forced near-expiry
   renewal per service with its reload checked.
3. The info page: nginx, the record, the redirects, HTTP with no redirect; render tests and the sandbox's page
   checks.
4. The image-update test and its fixture, run in the sandbox, then on the Pi.
5. The riding-along items; the full sandbox; then the release candidate on the test Pi, with the upgrade test
   0.6.2 → 0.6.3, the image-update test (arm64) and the host suite.
